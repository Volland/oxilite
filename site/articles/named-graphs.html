Graphs that describe graphs

A knowledge graph usually holds more than data: the ontologies that give it meaning and the shapes that keep it honest. oxilite now records which graph is which, and which data each schema describes, as plain RDF in a named graph of its own, with a published vocabulary. Your schema setup travels with your data and works on any SPARQL store.

A design note · Available on main, shipping in the next release · Every example is asserted by schema_registry.rs, registry_portability.rs and the CLI tests · Reference: docs/schema-registry.md

Named graphs are the unit of meaning

RDF gives you one tool for saying "these triples belong together": the named graph. People use it for provenance (one graph per source), for tenancy (one per customer), for versions, and for schema: the HR ontology in one graph, the product ontology in another, SHACL shapes in a third.

The store, though, has no idea which of those graphs are schema. An ontology is just more triples. Reasoners then do the only thing they can: they treat every rdfs:subClassOf anywhere in the dataset as an axiom that applies everywhere. Load two datasets whose ontologies disagree, and every entity ends up inheriting from both.

oxilite's schema registry fixed the first half of that problem by letting a graph declare its role. It kept that declaration in a private SQL table, and that had a price:

  • SPARQL could not see it;
  • a dump lost it;
  • it could not say which data an ontology is for.

The registry is now RDF.

1The registry is a named graph

Registrations live in the system graph <oxilite:schema>. Each registered graph is described there, with the graph's own IRI as the subject:

PREFIX oxl: <https://oxilite.dev/ns#>

GRAPH <oxilite:schema> {
  <https://ex.org/onto/zoo> a oxl:OntologyGraph ;
      oxl:appliesTo <https://ex.org/data/zoo> ;
      oxl:active true ;
      oxl:version "2.1" ;
      oxl:loadedAt "2026-09-26T10:00:00Z"^^xsd:dateTime .

  <https://ex.org/shapes> a oxl:ShapesGraph .     # no oxl:appliesTo: every graph
}

Nothing about the ontology graph itself changes: its triples stay where you loaded them, ordinary RDF that SPARQL reads and updates. The registry is a description about graphs, which is exactly what RDF is good at.

Because it is just triples, registering a graph is just an update. This is a complete registration, on oxilite or anywhere else:

INSERT DATA { GRAPH <oxilite:schema> {
  <https://ex.org/onto/zoo> a oxl:OntologyGraph ; oxl:appliesTo <https://ex.org/data/zoo> .
} }

oxilite notices the write, and in the same atomic request rebuilds what depends on it: the reasoning closure and the SHACL shape index.

2Map each schema to the data it describes

oxl:appliesTo is the new idea. It names the graphs a schema describes: graph IRIs, oxl:DefaultGraph, or oxl:AllGraphs. Leaving it out means every graph.

That is what lets two datasets with conflicting ontologies share one store:

# ontology graphs                         # data graphs
ex:zoo-onto     ex:Dog ⊑ ex:Animal        ex:zoo      ex:rex  a ex:Dog
ex:garden-onto  ex:Dog ⊑ ex:Plant         ex:garden   ex:fido a ex:Dog   # a snapdragon cultivar
ex:common       ex:Animal ⊑ ex:Being , ex:Plant ⊑ ex:Being
$ oxilite registry register http://ex.org/zoo-onto    --role ontology --applies-to http://ex.org/zoo    -l kg.sqlite
$ oxilite registry register http://ex.org/garden-onto --role ontology --applies-to http://ex.org/garden -l kg.sqlite
$ oxilite registry register http://ex.org/common      --role ontology -l kg.sqlite

$ oxilite query -l kg.sqlite --reasoning rdfs -q 'SELECT ?x { GRAPH ?g { ?x a ex:Animal } }'   # ex:rex
$ oxilite query -l kg.sqlite --reasoning rdfs -q 'SELECT ?x { GRAPH ?g { ?x a ex:Plant } }'    # ex:fido
$ oxilite query -l kg.sqlite --reasoning rdfs -q 'SELECT ?x { GRAPH ?g { ?x a ex:Being } }'    # both

Each triple is entailed with the axioms that apply to its own graph: the zoo ontology for zoo data, the garden ontology for garden data, and the common ontology for both. This holds even when the query reads every graph at once, with GRAPH ?g or a union default graph. schema_graphs_for(graph, role) answers the same question from code: which active ontologies (or shapes) apply to this graph?

Under the hood, the TBox closure is kept per scope:

  • one closure for all graphs;
  • one more for each graph that has ontologies of its own, built from those ontologies plus the global ones.

Closures do not compose across ontologies, so each scope gets a full one. That costs little, because a TBox is small. The query rewrite then joins each quad with the closure of its graph. A store that maps nothing pays one extra equality on an indexed column, and nothing else.

3System graphs, and the ontology of the registry

A registry written in a vocabulary should carry that vocabulary. So oxilite now keeps two system graphs, both typed oxl:SystemGraph in the registry:

GraphHolds
<oxilite:schema>The registry: what every registered graph is and where it applies, including a description of itself
<oxilite:vocabulary>The oxl: ontology: classes, properties and their documentation, declared to apply to <oxilite:schema>

A database the oxilite command line creates starts with both, so the registry is self-describing from its first write:

$ oxilite new.sqlite
oxilite> SELECT ?class ?label { GRAPH <oxilite:vocabulary> { ?class rdfs:subClassOf oxl:SchemaGraph ; rdfs:label ?label } } ORDER BY ?class
┌───────────────────┬────────────────────┐
│ class             │ label              │
├───────────────────┼────────────────────┤
│ oxl:OntologyGraph │ ontology graph     │
│ oxl:ShExGraph     │ ShEx schema graph  │
│ oxl:ShapesGraph   │ SHACL shapes graph │
│ oxl:SystemGraph   │ system graph       │
└───────────────────┴────────────────────┘
4 rows

The libraries leave a new store empty by default. @oxilite/node and the Rust crate are drop-in replacements for Oxigraph, and an Oxigraph store starts empty. You opt in with one flag:

// Rust
Store::open_with_options("kg.sqlite", StoreOptions { system_graphs: true, ..Default::default() })?;
// Node
new Store({ path: "kg.sqlite", systemGraphs: true });
// Cloudflare D1 (or: npx oxilite-d1 schema --system-graphs > migrations/0001.sql)
await D1Store.open(env.DB, { wasm, systemGraphs: true });

An existing database gets them with oxilite registry init, install_system_graphs() or installSystemGraphs(). Each of these does nothing when the installed vocabulary is already current.

System graphs are part of the dataset, but they are not registrations:

  • schema_graphs() does not list them;
  • they never narrow reasoning or the shape index;
  • they stay out of the "every graph" fallback;
  • include_schema_graphs: false hides them along with the schema they describe.

The vocabulary is published on its own at oxilitedb.com/ns, as a readable page and as Turtle.

4The same setup on Oxigraph

Every registry operation is SPARQL 1.1, which the core generates. Register, map, deactivate, unregister, drop, install the system graphs: all are plain updates, and listing is one SELECT. A test runs that exact text on a real Oxigraph store and checks three things:

  • Oxigraph reads back the same registration;
  • it ends up with the identical <oxilite:schema> graph oxilite writes;
  • installing the system graphs there leaves the same quads as a bootstrapped blank oxilite store.

Oxigraph does not reason, but everything that describes your schema is portable:

  • an N-Quads dump carries it;
  • a validator pointed at Oxigraph can find the shapes for a graph;
  • any tool can ask which ontologies apply where.
# which active ontologies describe ex:staff? (any SPARQL store)
SELECT ?onto WHERE { GRAPH <oxilite:schema> {
  ?onto a oxl:OntologyGraph .
  FILTER NOT EXISTS { ?onto oxl:active false }
  FILTER (NOT EXISTS { ?onto oxl:appliesTo ?any }
       || EXISTS { ?onto oxl:appliesTo <https://ex.org/data/staff> }
       || EXISTS { ?onto oxl:appliesTo oxl:AllGraphs })
} }

Everywhere you work

The registry used to be Rust-only. Every surface now reaches it, and every one runs the same SPARQL underneath:

SurfaceRegister and mapReason
Shell.register ontology ex:onto onto.ttl, .map ex:onto ex:data, .registry, .shapes.reasoning rdfs, .schemagraphs off

Upgrading

Stores created by 0.4 kept registrations in a schema_graphs table. Opening one migrates it in a single atomic request:

  • each row becomes triples of <oxilite:schema>;
  • the table is dropped;
  • the closure cache gains its scope column.

On D1, the migration runs on D1Store.open(). A store that registers nothing behaves exactly as before: every graph's axioms apply to every graph.

Limits to know

  • Graphs named by blank nodes cannot be registered. Another graph has no way to name them.
  • Mappings drive query-time reasoning. OWL 2 RL materialize() still reasons over the merged dataset. The class-keyed shape index behind Cypher ignores shapes mappings; validators can use schema_graphs_for.
  • owl:imports is recorded, not followed.
  • On a versioned store, the system graphs and the 0.4 migration are written outside the change log.
  • The namespace is https://oxilite.dev/ns# (shared with oxl:textMatch and the history graph). The document describing it lives at oxilitedb.com/ns.

The takeaway. Which graphs are schema, and which data each schema describes, is now data too: triples in <oxilite:schema>, in a vocabulary the store carries in <oxilite:vocabulary>. Reasoning follows the mapping graph by graph, and the whole setup moves with a dump and runs as plain SPARQL on Oxigraph.
