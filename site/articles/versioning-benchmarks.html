How much does versioning slow oxilite down?

oxilite can keep a store's history: commits with authors and messages, and SPARQL and Datalog on any past version. That memory has a price, and this article measures it. Queries on the present cost the same. Writes cost a little more. Reading the past costs from about 1× to over 100× the present, depending on the query and on one index.

Benchmarks · Apple M2 Max, bundled SQLite in memory, median of 15 runs after a warm-up · D1 write costs on a local D1 (Miniflare) · Reproduce with as-of-latency and write-cost; raw results in bench/results

What versioning does, in one paragraph

A store chooses a level, and the choice is recorded in the database:

  • off, the default, changes nothing.
  • stamped adds a store clock. Every write becomes a tick with a time, an author and a message, and every quad records the tick that added it.
  • log adds an immutable change log, written by triggers under the quad table. Queries can then read any past version (as_of: "HEAD~3", "#42", "@2026-09-01T12:00:00Z"), compare two versions in one query (SERVICE <oxilite:version/HEAD~1>), and list, diff and stream changes.

The use cases being measured

The benchmark is shaped by what versioning is for:

  • Agent memory. What did the agent believe at 14:02, which tool wrote it, and what did that ingestion change? The queries are selective lookups and joins at a past time.
  • Curated graphs and ontologies. Review diffs and attribution per commit. These are diffs and lookups a few commits back.
  • Audit. What did we know when the decision was made? These are the same queries, far back in time.
  • Change feeds. Search indexes, caches and exports want what changed since the last sync. That needs stamped or log, and it is a read by tick.
  • Reproducible analysis. Pin a report to a tick. This is the heaviest case: aggregates over the store as it was.

The setup

The data is a synthetic ticket tracker, built the same way at four levels:

  • Tickets with a type, an owner, a priority and a status, four triples each, bulk-loaded.
  • Commits after the load. Each is one SPARQL update that moves the status of 20 random tickets and adds a two-triple comment. That is the shape of an application's history: a big import, then many small writes.

Four queries are timed on the present, on the latest version read through the log (HEAD), and at several depths:

QueryShapeStands for
subject lookup<t123> ?p ?o"what did we know about this entity"
value lookup?t :status "blocked""which entities had this value"
star joinfour patterns on one ticket, counteda typical selective query
group bycount tickets per statusan aggregate over a whole predicate: reports, dashboards

The main configuration is 20,000 tickets (80,000 triples) and 500 commits, which gives 95,724 log rows. It is repeated at 2,000 commits (143,502 log rows) and at 100,000 tickets (400,000 triples, 415,656 log rows). Three repeated runs of the main configuration agree within about 5 %.

Writes: a little more

On D1, writes are billed per row written, index entries included. write-cost loads 5,000 triples into a local D1 at each level:

LevelRows written per triplevs. off
off4.81—
stamped4.82+0.2 % (three rows per batch: the tick and its time term; none per triple)
log6.82+42 %
log + as-of index8.82+83 %

Wall time and size on the bundled SQLite, for the main configuration:

LevelBulk load, 80k triplesOne commitDatabase size
off347 ms15.8 ms12.8 MB
stamped362 ms15.9 ms13.0 MB (+2 %)
log685 ms (2.0×)16.6 ms (+5 %)20.2 MB (+58 %)
log + as-of index792 ms (2.3×)17.2 ms (+9 %)27.2 MB (+113 %)

A commit is dominated by evaluating the update's WHERE. The triggers that append to the log add a few percent. A bulk load writes every triple twice, into the store and into the log, so it takes about twice as long. The log also grows with the history: at 2,000 commits the plain log store is 24.3 MB against 13.3 MB without versioning. stamped is close to free everywhere. Its stamp lives in the quad row itself, and D1 bills rows, not bytes.

The present: unchanged

Queries without a version read the quad table, exactly as an unversioned store does. In every configuration measured, their time is the same as off within noise. A golden test pins their SQL for the W3C query corpus to the SQL of the release before versioning. If you only query the present, versioning costs you nothing at read time.

The past: it depends on one index

A past version is computed from the log: the quads whose latest change at or before the tick is an addition. That is a log scan with one probe per candidate row. The main configuration, 250 commits back:

QueryPresentPast, plain logPast, log + as-of index
subject lookup0.02 ms0.06 ms (3.0×)0.07 ms (3.1×)
value lookup1.86 ms19.0 ms (10×)2.12 ms (1.2×)
star join0.18 ms17.6 ms (99×)0.60 ms (3.4×)
group by0.91 ms25.0 ms (27×)15.2 ms (16.5×)
  • The subject is bound: about 3×, index or not. The log's key starts with the subject, so the version is read from a handful of log rows. The factor is the extra probe per row.
  • Only the predicate or object is bound: 10–100× without the as-of index, 1–3.4× with it. Without it, nothing leads to the matching rows, so the whole log is scanned. The as-of index adds predicate-first and object-first orders, so the past is read the way the present is.
  • Aggregating a whole predicate: about 16× even with the index. The query has to consider every historical row of :status, not just the current ones, and each pays a probe. The index narrows the scan, but it cannot avoid it.

How the cost grows

With the store. At 400,000 triples and 500 commits, 250 commits back:

QueryPresentPlain log+ as-of index
value lookup2.35 ms82.3 ms (35×)2.57 ms (1.1×)
star join0.96 ms82.7 ms (86×)2.85 ms (3.0×)
group by4.40 ms116 ms (26×)59.8 ms (13×)

Without the index the cost follows the size of the log, so it grows with the store. With the index, selective queries keep their factor as the store grows five-fold.

With the history. At 2,000 commits instead of 500 (143,502 log rows), 1,000 commits back:

QueryPresentPlain log+ as-of index
subject lookup0.02 ms0.12 ms (5.7×)0.12 ms (5.8×)
value lookup4.58 ms31.1 ms (6.8×)8.08 ms (1.8×)
star join0.14 ms27.1 ms (200×)0.63 ms (4.8×)
group by0.88 ms38.7 ms (44×)30.8 ms (34×)

A longer history hurts in two ways:

  • Frequently changed quads. Each has more log rows to skip over, so even the subject lookup rises from 3× to about 6×.
  • Whole-history aggregates. They grow with the history, from 16× to 34× here.

Selective queries with the index stay within 5× of the present.

With depth. Reading further back is cheaper: fewer log rows are visible at an older tick. In the main configuration with the index, the value lookup costs 3.4 ms at HEAD, 2.0 ms 250 commits back and 0.7 ms at the oldest commit. Without the index the same query goes from 22 ms to 15 ms. Asking for the present through the log (as_of: "HEAD") is the most expensive way to read it, so don't: omit the version.

What will make the slow cases faster

The one case that stays expensive is an aggregate over a predicate's whole history, and it grows with the history. The fix is checkpoints: materialize a version every n commits, then read a past version as the nearest checkpoint plus the changes after it. That bounds the scan by n instead of by the whole history. It is the first design question for branches and merge, because they read every branch that is not checked out through the log. It will be settled with a run of BEAR, the benchmark for versioned RDF archives, before branches are built.

Reproduce it

cargo run --release -p oxilite-bench --bin as-of-latency                # 20,000 tickets, 500 commits
cargo run --release -p oxilite-bench --bin as-of-latency -- 20000 2000   # a longer history
cargo run --release -p oxilite-bench --bin as-of-latency -- 100000 500   # a bigger store
node testsuite/d1-sidecar/server.mjs &                                  # a local D1
cargo run --release -p oxilite-bench --bin write-cost -- http://localhost:8787

The takeaway. Versioning never slows down the present. A store clock is close to free, and a full log costs 42 % more rows written and about 5 % more time per commit. The past is where the cost lives. It is about 3× for lookups by entity, and 1–5× for selective queries once you add the as-of index. Aggregates over a whole history remain the expensive case, and checkpoints are next.
