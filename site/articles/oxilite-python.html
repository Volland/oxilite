How to use oxilite with Python

Most knowledge-graph work happens in Python, in notebooks, pipelines and agent frameworks. oxilite now ships a Python package with pyoxigraph's API. It keeps the whole graph in one SQLite file, and the same data answers SPARQL, openCypher and Datalog.

A tutorial · Every snippet on this page comes from examples/python-tour/tour.py, which CI runs with the outputs asserted

Why a SQLite file

Python already has an excellent RDF store: pyoxigraph, Oxigraph's Python package. It stores data in RocksDB, as a directory of files that only RocksDB can read. That is the right choice for a server. It gets awkward when the graph must travel:

  • when you commit a fixture to a repository
  • when you attach a dataset to a notebook
  • when you ship a graph inside a desktop app
  • when you give each agent its own memory file
  • when you inspect a database with sqlite3

oxilite keeps Oxigraph's data model, SPARQL semantics and API, and stores everything in SQLite. Each query compiles to one SQL statement. The file can be copied, backed up and opened by any SQLite tool. On top of that, oxilite adds what pyoxigraph does not have:

  • openCypher and Datalog over the same quads
  • RDFS and OWL reasoning
  • a registry of ontologies and SHACL shapes
  • JSON-LD documents stored verbatim
  • Verifiable Credentials
  • a version history you can query

Install

pip install oxilite

That installs one prebuilt wheel, with SQLite compiled in. It needs no compiler and no system library. Wheels use CPython's stable ABI, so the same wheel serves Python 3.9 through the newest release, on:

  • Linux (x86_64 and aarch64, glibc and musl)
  • macOS (Intel and Apple silicon)
  • Windows (x64)

1A knowledge graph in one file

from oxilite import Literal, NamedNode, Quad, RdfFormat, Store

store = Store("team.sqlite")          # created on first use; Store() is in memory
store.load("""
    @prefix ex:   <http://example.org/> .
    @prefix foaf: <http://xmlns.com/foaf/0.1/> .

    ex:ada   a ex:Engineer ; foaf:name "Ada"   ; ex:age 36 ; foaf:knows ex:grace .
    ex:grace a ex:Engineer ; foaf:name "Grace" ; ex:age 45 ; foaf:knows ex:alan .
    ex:alan  a ex:Researcher ; foaf:name "Alan" ; ex:age 41 .
""", RdfFormat.TURTLE)

EX = "http://example.org/"
store.add(Quad(NamedNode(EX + "alan"), NamedNode(EX + "age"), Literal(42)))
store.remove(Quad(NamedNode(EX + "alan"), NamedNode(EX + "age"), Literal(41)))
len(store)                               # 11

Each piece of that code does one thing:

  • load accepts a string, bytes, an open file, or path="dump.nq", whose extension picks the format. It is atomic: a syntax error on line 900 leaves the store untouched, and the SyntaxError carries the file name, line and column. For millions of triples, bulk_load commits in chunks and refreshes the planner's statistics at the end.
  • Terms are plain Python values. Literal(42) is an xsd:integer. Terms can be hashed and pickled, and match statements destructure them.
  • An invalid IRI raises ValueError on the line that builds it, not deep inside a query.

2Ask it with SPARQL

PREFIXES = {"ex": EX, "foaf": "http://xmlns.com/foaf/0.1/"}

solutions = store.query(
    "SELECT ?name ?age WHERE { ?p foaf:name ?name ; ex:age ?age } ORDER BY DESC(?age)",
    prefixes=PREFIXES,
)
[v.value for v in solutions.variables]             # ['name', 'age']
[(s["name"].value, int(s["age"].value)) for s in solutions]
# [('Grace', 45), ('Alan', 42), ('Ada', 36)]

store.query("ASK { ex:ada foaf:knows ex:grace }", prefixes=PREFIXES)          # truthy
store.query("CONSTRUCT { ?b ex:knownBy ?a } WHERE { ?a foaf:knows ?b }", prefixes=PREFIXES)

Results come back in pyoxigraph's classes, one per query form:

  • QuerySolutions, for SELECT: an iterator of solutions, each readable by name, by position, by Variable, or by unpacking.
  • QueryBoolean, for ASK: usable as a bool.
  • QueryTriples, for CONSTRUCT and DESCRIBE: an iterator of triples.

Each one serializes to the standard results formats:

from oxilite import QueryResultsFormat, Variable

store.query("SELECT ?name WHERE { ?p foaf:name ?name } ORDER BY ?name", prefixes=PREFIXES
            ).serialize(format=QueryResultsFormat.CSV)
# b'name\r\nAda\r\nAlan\r\nGrace\r\n'

# Bind a variable before evaluation, without string formatting (no injection):
store.query("SELECT ?friend WHERE { ?p foaf:knows ?friend }", prefixes=PREFIXES,
            substitutions={Variable("p"): NamedNode(EX + "ada")})

# Rows as dicts, ready for pandas.DataFrame(rows) or a JSON API:
solutions = store.query("SELECT ?name ?age WHERE { ?p foaf:name ?name ; ex:age ?age }", prefixes=PREFIXES)
rows = [{v.value: s[v].value for v in solutions.variables} for s in solutions]

substitutions binds variables before the query runs. oxilite implements it by joining a one-row VALUES into the query's algebra, so the query is still a single SQL statement.

3See the SQL

Nothing is hidden. explain shows the statement a query becomes, and the join order the planner chose:

print(store.explain("PREFIX ex: <http://example.org/> "
                    "SELECT ?p WHERE { ?p a ex:Engineer ; ex:age ?a FILTER(?a > 40) }"))
-- oxilite: fully compiled to SQL (1 output variable(s))
-- join order (heuristics, run optimize() for statistics): ?p rdf:type ex:Engineer (~500 rows) → ?p ex:age ?a (~1 rows)
SELECT q1.s AS v0 FROM quads q1 CROSS JOIN quads q2
WHERE q1.p = 662360971285383673 AND q1.o = 1092603140165095980 AND +q1.g = 0
  AND q2.s = q1.s AND q2.p = 768773004378996546 AND +q2.g = 0
  AND (CASE … ((q2.o) & 576460752303423487) - 288230376151711744 … END) > (40)

Each detail in that SQL has a reason:

  • Constants are integers. Every term is a 64-bit hash computed in Rust, so the constants in the SQL are integers, and no dictionary lookup runs at query time.
  • Small numbers live in the id. Small integers are stored inside the id itself, so ?a > 40 is plain arithmetic, not a join.
  • The planner needs statistics. Run store.optimize() after a large import, and it orders joins from real per-predicate counts.

explain_update, explain_cypher and explain_datalog do the same for the other languages.

4Coming from pyoxigraph

import oxilite as pyoxigraph            # the only change most pyoxigraph code needs

legacy = pyoxigraph.Store("data/")       # an existing directory: the data goes to data/oxilite.sqlite

This is not a promise, it is a test. pyoxigraph's own test suite (test_store.py, test_model.py, test_io.py) runs against oxilite on every build with only the import changed. 112 tests pass. Three are listed as known divergences, and CI fails if any other test fails, or if a listed one starts passing:

pyoxigraph featureoxiliteWhy
custom_functions, custom_aggregate_functionsNotImplementedErrorA query is one SQL statement run by SQLite, which cannot call back into Python for each row
LOAD <https://…> in an updateNotImplementedErrorThe core does no network I/O. Download the file, then store.load(path=…)

The rest carries over:

  • RDF-star triple terms
  • default_graph and named_graphs datasets
  • use_default_graph_as_union
  • bulk_load
  • dump to paths and file objects
  • parse, serialize and parse_query_results
  • Store.read_only

5The same data, as a property graph

Some questions read better as graph patterns. cypher runs openCypher over the same quads. In that view:

  • nodes are IRIs
  • labels are rdf:type
  • properties are literal triples
  • relationships are triples
cy = {"base": EX, "prefixes": {"foaf": "http://xmlns.com/foaf/0.1/"}}
result = store.cypher(
    "MATCH (a)-[:`foaf:knows`]->(b) RETURN a.`foaf:name` AS who, b.`foaf:name` AS knows ORDER BY who", **cy)
result.records     # [{'who': 'Ada', 'knows': 'Grace'}, {'who': 'Grace', 'knows': 'Alan'}]

created = store.cypher(
    "MATCH (a {`foaf:name`: 'Alan'}) CREATE (a)-[:MENTORS {since: 2024}]->(:Engineer {`foaf:name`: 'Linus'})", **cy)
created.stats.nodes_created, created.stats.relationships_created     # (1, 1)
store.query('ASK { ?n foaf:name "Linus" ; a ex:Engineer }', prefixes=PREFIXES)   # truthy

How the two views map onto each other:

  • Names. base gives unprefixed labels and keys a namespace. prefixes lets you write `foaf:name`.
  • Relationship properties. A relationship with properties, such as since, gets an RDF 1.2 reifier. SPARQL sees everything Cypher writes, and Cypher sees everything SPARQL writes.
  • Results. Nodes and relationships come back as CypherNode and CypherRelationship dataclasses, and records are plain dicts.
  • Atomicity. A writing statement is atomic.

6Rules that recurse

Datalog handles questions that need recursion together with a join, a filter or a count. SPARQL property paths cannot express those. Here "reach" follows two predicates, one of them written a moment ago by Cypher:

program = """
@prefix ex:   <http://example.org/> .
@prefix foaf: <http://xmlns.com/foaf/0.1/> .
reach(?x, ?y) :- foaf:knows(?x, ?y).
reach(?x, ?y) :- ex:MENTORS(?x, ?y).
reach(?x, ?z) :- reach(?x, ?y), reach(?y, ?z).
?- reach(ex:ada, ?who).
"""
sorted(r["who"].value for r in store.datalog(program).records)
# ['http://example.org/alan', 'http://example.org/grace', 'urn:oxilite:node:…']   ← Linus

The program's parts:

  • Atoms. An IRI with two arguments is a triple pattern, and an IRI with one argument is a class.
  • Evaluation. Linear recursion compiles to a single WITH RECURSIVE statement. Other recursion is iterated to a fixpoint, and result.rounds reports how many rounds it took.
  • Rejected programs. A program with negation inside a recursive cycle raises ValueError naming the cycle, before any SQL runs.
  • Materializing. datalog_materialize(program) stores what the rules derive. Queries see those triples with include_inferred=True.

7Reasoning

store.update("""PREFIX ex: <http://example.org/> PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
    INSERT DATA { ex:Engineer rdfs:subClassOf ex:Person . ex:Researcher rdfs:subClassOf ex:Person . }""")

count = lambda **opts: len(list(store.query("SELECT ?p WHERE { ?p a ex:Person }", prefixes=PREFIXES, **opts)))
count(), count(reasoning="rdfs")                  # (0, 4)

store.materialize(engine="reasonable")             # OWL 2 RL closure, stored apart from the data
count(include_inferred=True)                        # 4

You have two options:

  • Reason at query time. reasoning="rdfs" (or "owl-ql") rewrites the query over the class and property hierarchies. Nothing is stored, so there is nothing to keep in sync.
  • Materialize. materialize() computes the full OWL 2 RL closure once and keeps it in a separate table. clear_inferences() drops it.

When ontologies live in named graphs, register_schema_graph(graph, "ontology", applies_to=[…]) scopes reasoning to the ontologies you trust and the graphs they describe. "shacl" graphs feed a compiled shape index that checks Cypher writes.

8JSON-LD documents and credentials

docs = store.jsonld()
key = docs.put('{"@context": {"name": "http://xmlns.com/foaf/0.1/name"}, '
               '"@id": "http://example.org/doc/1", "name": "Ada"}')
docs.get(key).json                     # the exact text you stored, byte for byte
store.query('ASK { GRAPH <http://example.org/doc/1> { ?s foaf:name "Ada" } }', prefixes=PREFIXES)

vcs = store.credentials()
vcs.put({
    "@context": ["https://www.w3.org/ns/credentials/v2"],
    "id": "urn:uuid:badge-1", "type": ["VerifiableCredential"],
    "issuer": "did:example:academy", "validFrom": "2024-01-01T00:00:00Z",
    "credentialSubject": {"id": "did:example:ada"},
})
[c.key for c in vcs.find(issuer="did:example:academy", valid_at=datetime.now(timezone.utc))]
# ['urn:uuid:badge-1']

Each document is stored as it was written, under its key. Its RDF goes in a named graph of the same IRI, and SPARQL queries that graph like any other. The rest follows from that:

  • Contexts. The W3C credential contexts are bundled, so nothing is fetched. network=True opts in to downloading other contexts.
  • Lookups. find answers by issuer, subject, type and validity from indexed columns, without SPARQL.
  • Types. Timestamps are timezone-aware datetimes. Errors raise JsonLdError, whose code is the JSON-LD error code.
  • Proofs. Proofs are kept in their own graphs, but oxilite does not verify them: verify them on the stored JSON with a verifier library.

9Time travel

tasks = Store("tasks.sqlite", versioning="log")
with tasks.commit(author="ada", message="open the ticket"):
    tasks.update('INSERT DATA { <http://example.org/t1> <http://example.org/status> "open" }')
with tasks.commit(author="grace", message="close it"):
    tasks.update('DELETE DATA { … "open" } ; INSERT DATA { … "done" }')

status = "SELECT ?s WHERE { <http://example.org/t1> <http://example.org/status> ?s }"
[s["s"].value for s in tasks.query(status)]                  # ['done']
[s["s"].value for s in tasks.query(status, as_of="HEAD~1")]   # ['open']

[(c.author, c.message) for c in tasks.history() if c.kind == "write"]
# [('grace', 'close it'), ('ada', 'open the ticket')]
for change in tasks.diff("HEAD~1"):
    print("+" if change.added else "-", change.quad)
# + <http://example.org/t1> <http://example.org/status> "done"
# - <http://example.org/t1> <http://example.org/status> "open"

With versioning="log", every write is a commit in an immutable change log. The history works like this:

  • Commits. with store.commit(…) records an author and a message on the writes in its block.
  • Reading the past. as_of works in SPARQL, Cypher and Datalog. A version is HEAD~n, a tick (#42), or an instant (@2026-09-01T00:00:00Z).
  • The present stays fast. Queries on the present keep the same SQL.
  • Erasure. purge removes data from the present and from the whole history, for erasure requests.

Versioning is opt-in per store. Without it, a store has no extra tables and pays no extra write cost.

10Threads, asyncio and web apps

async def main():
    # Store calls release the GIL, so a thread per call keeps the event loop free.
    return await asyncio.gather(*(asyncio.to_thread(lambda: list(store.query("SELECT * WHERE { ?s ?p ?o }")))
                                  for _ in range(4)))

A Store can be shared across threads. Every call releases the GIL while SQLite works, so readers in other threads keep running. Writes queue, since SQLite has one writer at a time. In a FastAPI or Flask app, open one store at startup and call it from your handlers. With asyncio, wrap calls in asyncio.to_thread.

Limits to know

  • Results are materialized. A query returns once its rows are decoded. For very large SELECTs, page with LIMIT and OFFSET.
  • No Python inside SPARQL. Custom functions and aggregates are refused, and remote LOAD is not supported (see step 4).
  • One writer. SQLite serializes writes. Batch them with extend or one update, or use bulk_load for imports.
  • Proofs are not verified. Credentials are checked for structure and stored, not cryptographically verified.
