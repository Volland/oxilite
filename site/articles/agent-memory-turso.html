Agent memory on Turso: vector search inside your knowledge graph

An AI agent's memory needs two lookups: what sounds like this, and what is connected to it. On Turso, oxilite does both in one store and one query. This guide builds an agent's long-term memory step by step: model memories as a graph, index their embeddings, recall them with SPARQL, then turn that into tools an agent can call.

Why Turso, and what you get

Turso is SQLite rewritten in Rust. It speaks SQLite's SQL, runs in-process, and adds what SQLite never had: vector types (vector32, vector64, vector8, vector1bit, sparse vectors) and distance functions (cosine, Euclidean, dot product, Jaccard). oxilite compiles SPARQL, openCypher and Datalog into SQL, and oxilite-turso is the backend that runs that SQL on Turso. On that backend, and only there, oxilite has vector indexes.

A vector index is not a separate system. Embeddings are ordinary RDF literals on your nodes, and a nearest-neighbour search is one more table in the query's FROM list. Everything around the search (who may see a memory, when it was written, who it is about, what else those people are connected to) is compiled into the same SQL statement.

Embed the questionYour model, outside oxilite: text in, [0.85, 0.2, …] out
k nearestSERVICE <oxilite:vector/memories> ranks embeddings by distance…
Graph patterns…in the same SQL statement: visible to this user, recent, about whom, connected to what
Rows for the prompttext, score, provenance: context the agent can explain

What this gives an agent:

  • One file, in-process. Facts, embeddings, index definitions and (optionally) history live in one database file inside the agent's process. There's no vector service to run and nothing to keep in sync.
  • Filters in the query, not after it. Access control, recency and scoping run in the same statement as the search, so rows the agent may not see never leave the database.
  • Recall that follows relationships. The search finds where to start, and the graph walks to the people, events and decisions those memories are about.
  • Indexes that can't drift. Triggers update the index in the same transaction as every write, whichever language made it.

1Install

For Rust, turn on the turso feature. cypher and datalog are optional, and this guide uses both:

# Cargo.toml
[dependencies]
oxilite = { version = "0.8", features = ["turso", "cypher", "datalog"] }
use oxilite::store::Store;

let store = Store::open_turso("agent-memory.db")?;   // or Store::new_turso() in memory

The command line includes Turso. Every command takes --turso:

cargo install oxilite-cli
oxilite --turso agent-memory.db                 # interactive shell
oxilite query --turso -l agent-memory.db -q '…'  # one query
oxilite serve --turso -l agent-memory.db        # SPARQL endpoint over HTTP

The rest of oxilite works unchanged on Turso: the Rust API, SPARQL 1.1, Cypher, Datalog, reasoning and versioning. The exceptions are listed under Limits.

2Model memory as a graph

A memory is a node with its text, its embedding, and edges to what it is about. Everything an agent will later want to filter or follow is a triple: the people and events a memory concerns, who may see it, when it was written, and which conversation it came from.

memory.ttl 
@prefix ex:  <http://example.com/> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

# Who and what the agent knows about
ex:alice   a ex:Person  ; ex:name "Alice" ; ex:worksFor ex:acme .
ex:bob     a ex:Person  ; ex:name "Bob"   ; ex:worksFor ex:acme .
ex:carol   a ex:Person  ; ex:name "Carol" ; ex:worksFor ex:globex .
ex:acme    a ex:Company ; ex:name "ACME" .
ex:globex  a ex:Company ; ex:name "Globex" .
ex:offsite a ex:Event   ; ex:name "ACME offsite" ; ex:city "Lisbon" ; ex:on "2026-10-05"^^xsd:date .

# Where memories came from
ex:chat12  a ex:Conversation ; ex:channel "slack" .
ex:mail7   a ex:Conversation ; ex:channel "email" .

oxilite load --turso -l agent-memory.db -f memory.ttl

Real embeddings have hundreds or thousands of dimensions. Four keep the example readable. Here they roughly mean travel, health, work, preferences.

Modelling choiceWhy
An embedding is a JSON array in a plain literalIt's ordinary RDF: it dumps, loads, versions and backs up with everything else. The index reads it and checks its length.
Keep ex:text next to the embeddingThe agent needs words for its prompt, not numbers. Recall returns the text directly.
ex:about edges to people and eventsThis is what lets recall expand: from a memory to the people involved to everything else about them.
ex:visibleTo on every memoryAccess control becomes a graph pattern, so it runs inside the search's query.
Typed dates (xsd:date)oxilite stores dates in a typed column, so recency filters compare numbers and never parse strings.
One embedding property per modelAn index has a fixed dimension count. When you change embedding models, write ex:embedding_v2 and give it its own index (see Running it).

3Create the vector index

An index definition is RDF too. It lives in the system graph <oxilite:vectors>, and inserting it builds the index, back-filled from the embeddings already in the store:

PREFIX oxl: <https://oxilite.dev/ns#>
PREFIX ex:  <http://example.com/>

INSERT DATA { GRAPH <oxilite:vectors> {
  <oxilite:vector/memories> a oxl:VectorIndex ;
    oxl:indexName  "memories" ;
    oxl:property   ex:embedding ;
    oxl:dimensions 4 ;
    oxl:metric     oxl:Cosine ;
    oxl:class      ex:Memory .        # optional: only memories are candidates
} }

The same index from Rust, from Cypher (Neo4j 5 syntax), or from the shell:

use oxilite::model::NamedNode;
use oxilite::vector::{Metric, VectorIndex};

store.create_vector_index(
    &VectorIndex::new("memories", NamedNode::new("http://example.com/embedding")?, 4)
        .metric(Metric::Cosine)
        .class(NamedNode::new("http://example.com/Memory")?),
)?;
CREATE VECTOR INDEX memories IF NOT EXISTS FOR (m:Memory) ON (m.embedding)
OPTIONS { indexConfig: { `vector.dimensions`: 4, `vector.similarity_function`: 'cosine' } }
oxilite> .prefix ex: <http://example.com/>
oxilite> .vector create memories ex:embedding 4 cosine --class ex:Memory
oxilite> .vector list

Choosing a metric and an element type

OptionValuesUse it when
oxl:metricoxl:Cosine (default)Most text embedding models. Direction matters, length doesn't.
oxl:EuclideanEmbeddings where magnitude carries meaning, or the model says to use L2.
oxl:DotProductNormalized embeddings, or models trained for inner product.
oxl:JaccardSparse bag-of-words vectors, with element type SparseFloat32. This one uses Turso's inverted-file index.
oxl:elementTypeoxl:Float32 (default), Float64Full precision.
oxl:Int8, oxl:Bit1Quantized: about 4× and 32× smaller, for large memories where a little recall loss is acceptable.
oxl:SparseFloat32Only non-zero elements are stored.
oxl:classany class IRIOnly instances of the class are candidates, so a search never returns a user or a document when you asked for memories.

4Recall with SPARQL: eight recipes

A search is a SERVICE clause naming the index. Its body is a set of triples on one blank node:

PredicateMeaning
oxl:queryThe query vector as a JSON array literal, or a node IRI, meaning "near this node's own embedding".
oxl:kHow many nearest nodes the search returns. The default is 10.
oxl:nodeBinds each result node. Join it with the rest of the query.
oxl:distanceThe metric's distance as xsd:double. Lower is nearer.
oxl:scoreA similarity where higher is nearer, as Neo4j defines it: cosine 1 − d/2, Euclidean 1/(1 + d²), dot product −d, Jaccard 1 − d.

The agent embeds its question ("what do I know about upcoming travel?") and gets [0.85, 0.2, 0.05, 0.1]. All the recipes below use that vector and these prefixes:

PREFIX oxl: <https://oxilite.dev/ns#>
PREFIX ex:  <http://example.com/>
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>

1. Nearest memories

SELECT ?memory ?text ?score WHERE {
  SERVICE <oxilite:vector/memories> {
    [] oxl:query "[0.85, 0.2, 0.05, 0.1]" ; oxl:k 5 ;
       oxl:node ?memory ; oxl:score ?score .
  }
  ?memory ex:text ?text .
}
ORDER BY DESC(?score)
memory  text                                             score
ex:m5   Carol booked a trip to Lisbon in October         0.9984
ex:m2   Alice is flying to Lisbon for the ACME offsite   0.9919
ex:m4   Bob is also going to the ACME offsite            0.9885
ex:m1   Alice prefers aisle seats on long flights        0.9733
ex:m6   The offsite agenda is due on Friday              0.6796

This is all that a standalone vector database can give you, and it has already gone wrong. The top hit is Carol's private memory, and the agent is talking to Alice.

2. Only what this user may see

SELECT ?text ?score WHERE {
  SERVICE <oxilite:vector/memories> {
    [] oxl:query "[0.85, 0.2, 0.05, 0.1]" ; oxl:k 20 ;
       oxl:node ?m ; oxl:score ?score .
  }
  ?m ex:visibleTo ex:alice ; ex:text ?text .
}
ORDER BY DESC(?score) LIMIT 3
text                                             score
Alice is flying to Lisbon for the ACME offsite   0.9919
Bob is also going to the ACME offsite            0.9885
Alice prefers aisle seats on long flights        0.9733

Over-fetch, then cut. oxl:k is applied inside the search, before the graph patterns around it. With oxl:k 3 this query would return two rows: the three nearest are m5, m2 and m4, and Alice may not see m5. Ask the index for more than you need (here 20), filter with the graph, and cut with LIMIT. If one class of node is always the target, oxl:class on the index restricts candidates before ranking, at no cost.

3. Recent and relevant

Recency and a relevance floor are two more conditions. Dates compare as numbers through oxilite's typed columns:

SELECT ?text ?at WHERE {
  SERVICE <oxilite:vector/memories> {
    [] oxl:query "[0.85, 0.2, 0.05, 0.1]" ; oxl:k 20 ;
       oxl:node ?m ; oxl:score ?score .
  }
  ?m ex:visibleTo ex:alice ; ex:text ?text ; ex:at ?at .
  FILTER(?at >= "2026-09-14"^^xsd:date && ?score > 0.8)
}
ORDER BY DESC(?score)
text                                             at
Alice is flying to Lisbon for the ACME offsite   2026-09-20
Bob is also going to the ACME offsite            2026-09-21

4. Follow the graph

This is the recipe that similarity alone can't do. Start from the relevant memories, find the event they are about, find everyone else involved in it, and bring back what the agent knows about each of them:

SELECT DISTINCT ?who ?fact WHERE {
  SERVICE <oxilite:vector/memories> {
    [] oxl:query "[0.85, 0.2, 0.05, 0.1]" ; oxl:k 20 ;
       oxl:node ?hit ; oxl:score ?score .
  }
  FILTER(?score > 0.9)
  ?hit ex:visibleTo ex:alice ; ex:about ?event .   # relevant, and Alice may see it
  ?event a ex:Event .                              # the offsite
  ?other ex:about ?event , ?person .               # everyone involved in it
  ?person a ex:Person ; ex:name ?who .
  ?m ex:about ?person ; ex:text ?fact ; ex:visibleTo ex:alice .
}
who    fact
Alice  Alice is flying to Lisbon for the ACME offsite
Alice  Alice prefers aisle seats on long flights
Bob    Bob is allergic to peanuts
Bob    Bob is also going to the ACME offsite

Look at the third row. Bob is allergic to peanuts is the least similar memory in the store (score 0.63, below everything in recipe 1), so no similarity threshold that keeps out noise would return it. But Bob is going to the same offsite, and an agent booking the team dinner needs to know. The graph found it by following who the relevant memories were about, not what they sounded like.

5. Where did this come from?

Provenance is a join away, so an agent can cite its sources ("you told me by email"):

SELECT ?text ?channel WHERE {
  SERVICE <oxilite:vector/memories> {
    [] oxl:query "[0.85, 0.2, 0.05, 0.1]" ; oxl:k 3 ;
       oxl:node ?m ; oxl:distance ?d .
  }
  ?m ex:text ?text .
  OPTIONAL { ?m ex:source ?src }
  OPTIONAL { ?src ex:channel ?channel }
}
ORDER BY ?d
text                                             channel
Carol booked a trip to Lisbon in October         email
Alice is flying to Lisbon for the ACME offsite   email
Bob is also going to the ACME offsite            slack

Each OPTIONAL has one triple pattern on purpose. On the current Turso release, an OPTIONAL with several patterns, or with a property path inside it, fails to parse (see Limits). Chaining single-pattern OPTIONALs works on every backend. So does a required property path such as ?m ex:source/ex:channel ?channel.

6. Who is this about?

Aggregates run on the search results like on any other rows. This is useful for deciding which entity an ambiguous question refers to:

SELECT ?name (COUNT(?m) AS ?memories) (MAX(?score) AS ?best) WHERE {
  SERVICE <oxilite:vector/memories> {
    [] oxl:query "[0.85, 0.2, 0.05, 0.1]" ; oxl:k 10 ;
       oxl:node ?m ; oxl:score ?score .
  }
  ?m ex:about ?p . ?p a ex:Person ; ex:name ?name .
}
GROUP BY ?name ORDER BY DESC(?best)
name   memories  best
Carol  1         0.9984
Alice  2         0.9919
Bob    2         0.9885

7. Property paths from each hit

SELECT DISTINCT ?text ?company WHERE {
  SERVICE <oxilite:vector/memories> {
    [] oxl:query "[0.85, 0.2, 0.05, 0.1]" ; oxl:k 4 ; oxl:node ?m .
  }
  ?m ex:text ?text ; ex:about/ex:worksFor/ex:name ?company .
}
text                                             company
Alice is flying to Lisbon for the ACME offsite   ACME
Alice prefers aisle seats on long flights        ACME
Bob is also going to the ACME offsite            ACME
Carol booked a trip to Lisbon in October         Globex

8. More like this

Give oxl:query a node instead of a vector, and the search uses that node's stored embedding. The node itself comes first at distance 0, so filter it out:

SELECT ?similar ?text ?score WHERE {
  SERVICE <oxilite:vector/memories> {
    [] oxl:query ex:m2 ; oxl:k 5 ; oxl:node ?similar ; oxl:score ?score .
  }
  ?similar ex:text ?text .
  FILTER(?similar != ex:m2)
}
ORDER BY DESC(?score)
similar  text                                       score
ex:m4    Bob is also going to the ACME offsite      0.9885
ex:m5    Carol booked a trip to Lisbon in October   0.9850
ex:m1    Alice prefers aisle seats on long flights  0.9404
ex:m6    The offsite agenda is due on Friday        0.7022

That is how an agent finds related tickets, links a new entity to one it already knows, and (in the next step) merges duplicate memories.

Check the plan

explain shows that the search really is part of the one statement. It's a derived table joined like any triple pattern:

oxilite explain --turso -l agent-memory.db -q '… recipe 1 …'
-- oxilite: fully compiled to SQL (2 output variable(s))
-- vector search on memories (cosine, 4 dimensions, k = 3)
-- join order (statistics): ?m <http://example.com/text> ?text (~6 rows)
SELECT q2.o AS v1, … FROM (SELECT s, MIN(d) AS d FROM (SELECT v.s AS s,
  vector_distance_cos(v.e, vector32('[0.85, 0.2, 0.05, 0.1]')) AS d FROM vec_memories v
  WHERE EXISTS (… rdf:type ex:Memory …)) GROUP BY s ORDER BY d, s LIMIT 3) AS knn1
JOIN quads q2 … WHERE knn1.s = q2.s AND q2.p = … AND +q2.g = 0

5Remember, consolidate, forget

Remember

Writing a memory is an ordinary insert. The index trigger picks up the embedding in the same transaction:

PREFIX ex:  <http://example.com/>
PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>

INSERT DATA {
  ex:m7 a ex:Memory ;
    ex:text "Alice asked for an aisle seat again" ;
    ex:about ex:alice ; ex:visibleTo ex:alice ;
    ex:at "2026-09-27"^^xsd:date ; ex:source ex:chat12 ;
    ex:embedding "[0.9, 0.1, 0.0, 0.38]" .
}

An embedding of the wrong length, or one that isn't a JSON array, fails the whole write, so a half-written memory can't exist:

error: SQL backend error: oxilite: vector index memories expects 4 dimensions

An index that silently skipped bad rows would return wrong answers without anyone noticing. This happens most often when someone switches embedding models and forgets the index, and the loud failure catches it on the first write.

Consolidate

Agents repeat themselves. Before (or after) storing a memory, look for a near-duplicate about the same entity:

SELECT ?older ?text ?score WHERE {
  SERVICE <oxilite:vector/memories> {
    [] oxl:query ex:m7 ; oxl:k 3 ; oxl:node ?older ; oxl:score ?score .
  }
  ?older ex:text ?text ; ex:about ?who .
  ex:m7 ex:about ?who .                      # about the same person
  FILTER(?older != ex:m7 && ?score > 0.99)
}
older  text                                        score
ex:m1  Alice prefers aisle seats on long flights   0.9999

The agent can then keep the older memory and add a timestamp, or replace it with a merged sentence and a new embedding. Both are one SPARQL update.

Forget

DELETE WHERE { ex:m7 ?p ?o }

The embedding leaves the index with the triple, in the same transaction. This holds for every write path: SPARQL DELETE, CLEAR GRAPH, the bulk loader, and Cypher CREATE/SET/DELETE. There is no re-indexing job to schedule. For a store that must be able to prove what it forgot, turn on versioning, which also works on Turso, and use its audited purge for erasure requests.

6Turn it into agent tools

An LLM agent needs a few narrow tools, not a SPARQL console. Here are remember and recall in Rust. The recall query is recipe 2 with the user and the vector filled in.

use oxilite::model::{Literal, Term};
use oxilite::sparql::QueryResults;
use oxilite::store::Store;
use oxilite::turso::TursoBackend;

/// An embedding as the JSON array literal the index reads.
fn vector_literal(v: &[f32]) -> String {
    let items: Vec<String> = v.iter().map(f32::to_string).collect();
    format!("[{}]", items.join(", "))
}

fn remember(store: &Store<TursoBackend>, id: &str, user: &str, text: &str,
            about: &[&str], at: &str, embedding: &[f32]) -> oxilite::Result<()> {
    let about: Vec<String> = about.iter().map(|a| format!("<{a}>")).collect();
    store.update(format!(r#"PREFIX ex: <http://example.com/>
        PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>
        INSERT DATA {{
          <{id}> a ex:Memory ; ex:text {text} ; ex:about {about} ;
            ex:visibleTo <{user}> ; ex:at "{at}"^^xsd:date ; ex:embedding "{vector}" .
        }}"#,
        text = Literal::new_simple_literal(text),     // quoted and escaped
        about = about.join(", "),
        vector = vector_literal(embedding),
    ))
}

fn recall(store: &Store<TursoBackend>, user: &str, question: &[f32], k: usize)
    -> oxilite::Result<Vec<(String, f64)>> {
    let q = format!(r#"PREFIX oxl: <https://oxilite.dev/ns#>
        PREFIX ex:  <http://example.com/>
        SELECT ?text ?score WHERE {{
          SERVICE <oxilite:vector/memories> {{
            [] oxl:query "{vector}" ; oxl:k {fetch} ; oxl:node ?m ; oxl:score ?score .
          }}
          ?m ex:visibleTo <{user}> ; ex:text ?text .
        }}
        ORDER BY DESC(?score) LIMIT {k}"#,
        vector = vector_literal(question),
        fetch = k * 4,                                   // over-fetch, then cut
    );
    let QueryResults::Solutions(rows) = store.query(q.as_str())? else { unreachable!() };
    let mut out = Vec::new();
    for row in rows {
        let row = row?;
        if let (Some(Term::Literal(t)), Some(Term::Literal(s))) = (row.get("text"), row.get("score")) {
            out.push((t.value().to_owned(), s.value().parse().unwrap_or(0.0)));
        }
    }
    Ok(out)
}
recall(&store, "http://example.com/alice", &[0.85, 0.2, 0.05, 0.1], 2)?
// [("Alice is flying to Lisbon for the ACME offsite", 0.9919),
//  ("Bob is also going to the ACME offsite", 0.9885)]

The user comes from your session, not from the model, so the model can't widen its own access. Expose the tools to the model with plain JSON Schema. The wrapper field names differ between LLM APIs, but the schema is the same:

{
  "name": "recall",
  "description": "Search long-term memory for facts relevant to a question. Returns memory texts, most relevant first.",
  "input_schema": {
    "type": "object",
    "properties": {
      "question": { "type": "string", "description": "What to remember, in natural language" },
      "k": { "type": "integer", "minimum": 1, "maximum": 20, "default": 5 }
    },
    "required": ["question"]
  }
}

Your tool handler embeds question with the same model that embedded the memories, then calls recall. A remember tool takes text and about, and a related tool can run recipe 4 so the model can ask "what else should I know?" explicitly. A complete turn looks like this:

  1. Recall before answering: recipe 2 for relevance, recipe 4 for context the question didn't mention.
  2. Answer, citing provenance (recipe 5) when the user asks "how do you know?".
  3. Remember new facts, each with ex:about edges to the entities it mentions.
  4. Consolidate in the background: the near-duplicate query from step 5.
  5. Forget on request, or when a memory expires, with DELETE.

Rank by relevance and recency: a host function

A FILTER on dates is a hard cut. For a soft preference for fresh memories, register a host function: Rust code that SPARQL, Cypher and Datalog can all call, while the rest of the query still compiles to SQL:

use chrono::NaiveDate;
use oxilite::functions::HostFunction;
use oxilite::model::{Literal, Term};

fn date(t: &Term) -> Option<NaiveDate> {
    match t { Term::Literal(l) => NaiveDate::parse_from_str(l.value(), "%Y-%m-%d").ok(), _ => None }
}

store.register_function(
    HostFunction::new("http://example.com/fn#decay", |args| {
        let age = (date(args.get(1)?)? - date(args.first()?)?).num_days() as f64;
        Some(Literal::from(0.5_f64.powf(age / 14.0)).into())   // halves every 14 days
    })
    .cypher_name("fn.decay")
    .arity(2, 2)
    .description("half-life weighting: 1.0 today, 0.5 after 14 days"),
)?;
PREFIX fn: <http://example.com/fn#>
SELECT ?text ?rank WHERE {
  SERVICE <oxilite:vector/memories> {
    [] oxl:query "[0.85, 0.2, 0.05, 0.1]" ; oxl:k 20 ; oxl:node ?m ; oxl:score ?score .
  }
  ?m ex:visibleTo ex:alice ; ex:text ?text ; ex:at ?at .
  BIND(?score * fn:decay(?at, "2026-09-28"^^xsd:date) AS ?rank)
}
ORDER BY DESC(?rank) LIMIT 3
text                                             rank
Bob is also going to the ACME offsite            0.699
Alice is flying to Lisbon for the ACME offsite   0.667
The offsite agenda is due on Friday              0.557

The four-day-old agenda reminder now beats the month-old seat preference, which pure similarity ranked higher. Host functions are also a good place for a policy check, a PII redactor, or a re-ranker. A function returns None for "no value", which SPARQL treats like any other evaluation error. Registered functions belong to the store handle and aren't saved in the database.

7Agents in Python, TypeScript, anything

The Python and Node packages don't expose vector indexes yet. Any language can still use them over HTTP: oxilite serve speaks the SPARQL 1.1 protocol, and with --turso every recipe above works as-is.

oxilite serve --turso -l agent-memory.db -b 127.0.0.1:7879
curl -s http://127.0.0.1:7879/query \
  -H 'Accept: application/sparql-results+json' \
  --data-urlencode 'query=PREFIX oxl: <https://oxilite.dev/ns#> PREFIX ex: <http://example.com/>
    SELECT ?text ?score WHERE {
      SERVICE <oxilite:vector/memories> { [] oxl:query "[0.85, 0.2, 0.05, 0.1]" ; oxl:k 2 ; oxl:node ?m ; oxl:score ?score }
      ?m ex:text ?text } ORDER BY DESC(?score)'

From a Python agent, using only the standard library:

import json, urllib.parse, urllib.request

ENDPOINT = "http://127.0.0.1:7879"

def sparql(query: str) -> list[dict]:
    body = urllib.parse.urlencode({"query": query}).encode()
    req = urllib.request.Request(f"{ENDPOINT}/query", data=body,
                                 headers={"Accept": "application/sparql-results+json"})
    with urllib.request.urlopen(req) as r:
        return json.load(r)["results"]["bindings"]

def update(text: str) -> None:
    req = urllib.request.Request(f"{ENDPOINT}/update", data=text.encode(),
                                 headers={"Content-Type": "application/sparql-update"})
    urllib.request.urlopen(req).close()          # raises HTTPError (400) on a bad embedding

def recall(user: str, embedding: list[float], k: int = 5) -> list[str]:
    rows = sparql(f"""PREFIX oxl: <https://oxilite.dev/ns#> PREFIX ex: <http://example.com/>
      SELECT ?text ?score WHERE {{
        SERVICE <oxilite:vector/memories> {{
          [] oxl:query "{json.dumps(embedding)}" ; oxl:k {k * 4} ; oxl:node ?m ; oxl:score ?score }}
        ?m ex:visibleTo <{user}> ; ex:text ?text .
      }} ORDER BY DESC(?score) LIMIT {k}""")
    return [row["text"]["value"] for row in rows]

Keep the endpoint private to the agent's host. It accepts updates, and it has no authentication of its own.

8The same index from Cypher and Datalog

SPARQL, Cypher and Datalog share one nearest-neighbour statement, so they agree on results by construction. Use whichever language your agent (or your team) already speaks.

Cypher uses Neo4j's procedure, so existing Neo4j queries port unchanged. node is a real graph node, and the pattern keeps going from it:

CALL db.index.vector.queryNodes('memories', 10, $question) YIELD node, score
MATCH (node)-[:visibleTo]->(:Person {name: 'Alice'})
MATCH (node)-[:about]->(p:Person)
RETURN node.text AS memory, p.name AS about, score
ORDER BY score DESC LIMIT 3
memory                                           about  score
Alice is flying to Lisbon for the ACME offsite   Alice  0.992
Bob is also going to the ACME offsite            Bob    0.988
Alice prefers aisle seats on long flights        Alice  0.973

Datalog has a built-in relation, nearest(index, query, k, ?node, ?rank), that rules use like any other fact. Rules give the "what else should I know?" question a name, and negation drops what the agent has already seen:

@prefix ex: <http://example.com/> .

recalled(?m)     :- nearest("memories", "[0.85, 0.2, 0.05, 0.1]", 3, ?m, ?rank).
seen(?m)         :- recalled(?m), ex:visibleTo(?m, ex:alice).
event(?e)        :- seen(?m), ex:about(?m, ?e), ex:Event(?e).
attendee(?p)     :- event(?e), ex:about(?m, ?e), ex:about(?m, ?p), ex:Person(?p).
unseen(?who, ?t) :- attendee(?p), ex:name(?p, ?who), ex:about(?m, ?p), ex:text(?m, ?t),
                    ex:visibleTo(?m, ex:alice), not seen(?m).

?- unseen(?who, ?t).
oxilite datalog --turso -l agent-memory.db -f followup.dl
who    t
Alice  Alice prefers aisle seats on long flights
Bob    Bob is allergic to peanuts

These are the two facts about the people going to the offsite that the travel search didn't surface. They are exactly what the agent should add to its context. Datalog returns a rank rather than a distance, because in oxilite's Datalog every value is a stored term. See Rules your SPARQL can't write for the language.

9Running it

TaskHow
See what's indexed.vector list in the shell, SHOW VECTOR INDEXES in Cypher, store.vector_indexes() in Rust: rows, dimensions, metric, and whether each index is built.
Query the definitionsSELECT * WHERE { GRAPH <oxilite:vectors> { ?i ?p ?o } }. Definitions are data.
Change the metricA SPARQL DELETE/INSERT of oxl:metric in <oxilite:vectors> rebuilds the index with the new metric.
Change embedding modelsWrite the new vectors to a new property (ex:embedding_v2), create an index on it, switch the SERVICE name in your queries, then drop the old index and DELETE WHERE { ?m ex:embedding ?e }. Both indexes answer queries during the migration.
Copy a storeDump and load with the Rust API. Definitions travel in <oxilite:vectors>, and store.sync_vector_indexes() builds them on the target.
Drop an indexstore.drop_vector_index("memories"), DROP INDEX memories in Cypher, or .vector drop memories. The embeddings stay as triples.
Audit what the agent knewCreate the store with --versioning log: every write is a commit with an author and a message, and --as-of HEAD~1 queries the graph as it was.
Back upIt's one database file, plus Turso's -wal file beside it. Copy both while no writer is running.

Limits

  • Dense search is an exact scan. Turso has an approximate index only for sparse vectors (Jaccard). Cosine, Euclidean and dot-product search scan the index table: exact, and quick up to around a hundred thousand vectors, which covers most per-agent memories. It is not an ANN index for a hundred million. When Turso ships a dense index, it plugs into the one place oxilite writes nearest-neighbour SQL.
  • Turso only. Bundled SQLite, a system libsqlite3 and Cloudflare D1 have no vector functions, so creating an index or running a vector SERVICE there fails with an error that names Turso. For agents on Workers, see graph memory on Durable Objects.
  • Multi-pattern OPTIONAL on Turso. Turso 0.8.0-pre.14 doesn't parse the parenthesized join that an OPTIONAL with more than one pattern (or a path inside one) compiles to. Chain single-pattern OPTIONALs instead, as in recipe 5.
  • No full-text index on Turso. FTS5 isn't available there, so oxl:textMatch has no index.
  • A prerelease engine. oxilite pins Turso 0.8.0-pre.14 exactly, because recursive queries need it. The pin moves when Turso 0.8.0 is released.
  • Embeddings come from you. oxilite stores and searches vectors. Your application computes them, with the same model for memories and questions.
  • Rust, the CLI and HTTP. The Python and Node packages don't expose vector indexes or host functions yet (use oxilite serve --turso), and oxilite mcp doesn't open Turso stores.

The takeaway. Similarity tells an agent where to look. The graph tells it what's there, who may see it, and what else it should know. On Turso, both run in one query.
