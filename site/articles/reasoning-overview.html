One graph, seven reasoners: which one, when, and why

oxilite can reason over the same quads in six ways and check them in a seventh: RDFS and OWL QL at query time, OWL 2 RL materialization, Datalog, Synalog, Notation3, λProlog, and SHACL/ShEx. That can look like too many. This article explains why each one exists, how they share one store, and which to reach for, with a comparison matrix at the end.

An overview · The capabilities below are the ones the test suites check; each engine has its own guide, linked from its section

Why more than one

"Reasoning" covers several jobs, and no single engine is good at all of them:

  • Entailment from an ontology. "Every ex:Dog is an ex:Animal." The rules are fixed by the W3C specs; you write axioms, not rules.
  • Rules you write. "An ancestor is a parent, or a parent's ancestor." The logic is yours, and it often needs recursion, negation or aggregates.
  • Questions about something that isn't there. "If Dan had a child, would she be Ada's descendant?" That needs hypothetical reasoning.
  • Checks. "Every person has a name." That is a closed-world question about the data as it is, not a conclusion to add.

The engines also differ in where they run. Some compile to SQL and run inside SQLite, close to the data: those scale and work on Cloudflare D1, where every request is a network hop. Others run in memory: they are more expressive but have to load what they reason over. So oxilite doesn't pick one. It gives every engine the same store and the same place to put its conclusions, so they can be combined.

What they share

Every engine reads the same quad table. The ones that conclude something can write it into one inference table, quads_inf, beside the asserted data rather than into it. Each conclusion is attributed to the producer that derived it: owl2rl, a Datalog producer, n3, elpi, or a name you choose. This gives you three things:

  • Queries opt in. SPARQL, Cypher and Datalog read inferences only with include_inferred, so a query can always ask "what was asserted?"
  • Producers are independent. Re-running one producer replaces its own conclusions and leaves the others' in place. A quad two producers derive stays until neither does. inference_producers(quad) names who derived it.
  • Engines compose. An engine run with include_inferred reads the other producers' conclusions as input, but never its own. OWL 2 RL can feed Datalog, Datalog can feed N3, and so on.

The schema registry adds one more shared piece: it says which graphs hold ontologies and shapes, and which data graphs each applies to. That is how query-time reasoning and validation pick the right schema for each graph.

The seven, one by one

1. RDFS and OWL QL at query time

Turn it on per query (reasoning: Rdfs or OwlQl) and each triple pattern also matches what the ontology entails: subclasses, sub-properties, inverses, domains and ranges, transitive properties. Nothing is stored. A small closure of the ontology (tbox_closure) is kept up to date as the schema changes, and the compiler rewrites each query so it is still one SQL statement. Ontologies can be scoped per data graph through the registry.

Use it when you have an ontology and want queries to "just see" its consequences, on any backend, with no materialization to keep in sync.

2. OWL 2 RL materialization

materialize() computes the OWL 2 RL closure (equality, property axioms, class expressions, property chains) and stores it as the owl2rl producer. It runs as SQL rounds on every backend, D1 included, or in memory with the reasonable reasoner, which is much faster on large native stores.

Use it when you need more of OWL than query rewriting covers (owl:sameAs, property chains, owl:hasValue…), and when the conclusions should be stored and fast to read.

3. Datalog

RDF-native rules, ancestor(?x, ?z) :- ex:parent(?x, ?y), ancestor(?y, ?z)., with stratified negation and aggregates. A program compiles to one SQL statement where SQLite allows it, and is iterated in a work table where it doesn't. Results can be returned or materialized as a producer. It runs on every backend and from Rust, the CLI, Node, Python and D1. Datalog guide →

Use it for your own recursive rules over large data, especially on D1, where running inside SQLite saves round trips.

4. Synalog

The Datalog-family language for AI agents: named arguments, expressions, head aggregation, ordered and pageable results, and a verifier whose messages are written for a model. It reads triples as relational tables and returns SQL values, not RDF terms, so it doesn't materialize. Synalog guide →

Use it when an agent builds a semantic layer of named concepts over the graph and wants tabular, pageable answers.

5. Notation3

W3C-community rules over triples, { … } => { … }, run in memory by eyeron. N3 has builtins for math, strings, lists and time, scoped negation, backward rules, queries, proofs, and fuses (=> false) that stop a run on forbidden data. A run reads only the predicates its rule bodies use. Ask what follows, or materialize as a producer, on every backend including D1. N3 guide →

Use it when the rules come from the Semantic Web world or must be exchanged as standard N3, when you need builtins or proofs, or when a forbidden pattern must stop materialization.

6. λProlog (ELPI)

A full logic programming language run by lean-elpi: higher-order predicates, local assumptions (=>), fresh names (pi), cut and negation as failure, arithmetic on stored numbers. It reads the store on demand through ox.triple, one scan per call. It answers goals, reports violations (ox.violation) and materializes (ox.conclude). Native library; blocking stores only. λProlog guide →

Use it for "what if" questions, for checks that need recursion or computation, and for logic too rich for first-order rules.

7. SHACL and ShEx

Not inference but validation: rudof's engines check the data against shapes, which can be registered per graph. Reports are standard SHACL validation reports. D1 is validated from native code with a bounded prefetch.

Use it to state and enforce what the data must look like, in a standard others can read. Reach for λProlog checks or N3 fuses only when a rule is beyond SHACL.

Combining them

Because every producer writes to the same table and reads the others' output, a realistic pipeline uses several:

store.materialize()?;                                  // 1. OWL 2 RL closure      (producer owl2rl)
store.datalog_materialize(reachability)?;              // 2. recursive rules        (a Datalog producer)
store.n3_materialize_with(policies,                    // 3. N3 policies on top, with a fuse
    &Options { include_inferred: true, ..Default::default() })?;
let violations = store.elpi_check(checks)?;            // 4. checks that compute
// 5. queries opt in to everything above with include_inferred

When the ontology changes, re-run step 1. When a policy changes, re-run step 3; the closure and the Datalog conclusions are untouched. Queries can always ask for asserted data only.

The takeaway. There are several reasoners because reasoning is several jobs: entailment from an ontology, rules you write, "what if" questions and checks. Each engine is best at one of them, and some can run where the data is while others need memory. They share one store and one inference table, and conclusions are attributed per producer. So you can pick the right engine for each rule, combine several, and still ask what was asserted.
