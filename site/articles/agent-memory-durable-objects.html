Graph memory for AI agents on Durable Objects

Give every agent its own knowledge graph: a Durable Object that stores RDF in its embedded SQLite and answers SPARQL. That takes about 100 lines of TypeScript and no extra infrastructure.

A step-by-step guide · The full, tested example is in examples/do-agent-memory-ts

Why an agent needs a graph

Most agent memory today is a vector index: chunks of past conversations, found by similarity. Similarity search is good at "find something like this". It is weak at the questions an agent actually has to answer to act on the user's behalf:

  • Questions that follow relationships. "Which time zone should I use for the meeting with Maria?" needs four facts: Maria works at Acme, Acme is part of Globex, Globex is headquartered in Berlin, Berlin is on Europe/Berlin time. These facts came up in different conversations, and none of them mentions the other three. A vector search for "Maria meeting" finds none of the last three. A graph query follows the edges.
  • Knowing where a fact came from. Did the user say this, or did a CRM export? When? An agent that can't tell a user's statement from a scraped web page will eventually act on the wrong one. In RDF, every fact can sit in a named graph that records its source.
  • Changing its mind. People change their preferences, jobs and addresses. A graph lets the agent replace a fact in one atomic update (delete the old value, insert the new one) instead of piling up contradicting text chunks and hoping retrieval picks the latest.
  • Exact answers. "How many open tickets does this customer have?" is a count, not a similarity score. Graph queries return exactly what matches, and the query can be shown to a person and checked.
  • Shared meaning. An ontology can say that an Employee is a Person, or that manages is the inverse of reportsTo. oxilite applies RDFS and OWL rules at query time, so the agent doesn't have to store every implied fact.

None of this replaces vector search. The two work well together: embeddings find the entry point ("which node is this conversation about?") and the graph answers the structured question from there.

Why a Durable Object

A Durable Object is a small, stateful server that Cloudflare runs for you. Each object has a unique name, handles its requests one at a time, and can have its own SQLite database stored next to it. That fits agent memory unusually well:

PropertyWhat it gives agent memory
One object per nameidFromName("ada") always reaches the same object, so each agent or user gets a private graph. There are no tenant filters to forget.
Embedded SQLiteSQL runs in the same process as your code. oxilite's 1–2 statements per query cost local SQLite time, not network round trips.
One request at a timeTwo tool calls can't interleave their writes, and transactionSync makes a multi-statement write atomic.
HibernationAn idle object costs nothing. The graph stays on disk and is there the next time the agent wakes up.

D1 is still the better choice for one large, shared graph that many Workers read. A Durable Object is the better choice for many small, private graphs, one per agent, user or conversation. oxilite's core doesn't care which one you pick, as the next section shows.

How it works

oxilite's core is sans-IO: it turns SPARQL into SQL requests and turns rows back into results, but it never touches a database itself. The @oxilite/d1 package runs that core as WebAssembly and needs only two calls from its database: prepare(sql).raw() for a read, and batch(statements) for an atomic write. A Durable Object's ctx.storage.sql can provide both.

1Configure the Worker

Declare one Durable Object class and bind it as MEMORY. The new_sqlite_classes migration gives the class SQLite storage.

wrangler.toml 
name = "oxilite-agent-memory"
main = "src/index.ts"
compatibility_date = "2026-08-01"

[[durable_objects.bindings]]
name = "MEMORY"
class_name = "GraphMemory"

[[migrations]]
tag = "v1"
new_sqlite_classes = ["GraphMemory"]

Install the package with npm install @oxilite/d1. It contains the WebAssembly core, so the project needs no Rust toolchain.

2Adapt the object's SQLite

This is the only new piece. It presents ctx.storage.sql in the shape the oxilite driver expects:

  • a read is one exec, returned as arrays of column values;
  • an atomic batch runs inside transactionSync, so it commits entirely or not at all;
  • each statement reports how many rows it changed, measured with total_changes(), because the core uses those counts (for example, to tell whether a graph already existed).
src/do-sql.ts 
import type { D1DatabaseLike } from "@oxilite/d1";

interface Statement {
  sql: string;
  raw(): Promise<unknown[][]>;
}

export function durableObjectDatabase(storage: DurableObjectStorage): D1DatabaseLike {
  const exec = (sql: string) => storage.sql.exec(sql).raw().toArray() as unknown[][];
  const totalChanges = () => Number(exec("SELECT total_changes()")[0][0]);
  return {
    prepare(sql: string): Statement {
      return { sql, raw: async () => exec(sql) };
    },
    async batch(statements) {
      return storage.transactionSync(() =>
        (statements as Statement[]).map((s) => {
          const before = totalChanges();
          const rows = exec(s.sql);
          const changes = totalChanges() - before;
          // The driver reads each row with Object.values(), which returns an array's items in order.
          return { results: rows as unknown as Record<string, unknown>[], meta: { changes } };
        }),
      );
    },
  };
}

The adapter is short because the hard parts stay in the core: the SQL it generates already fits SQLite without extensions, keeps every write inside one batch, and selects 60-bit term ids as text so JavaScript numbers don't lose precision. The SQLite limits oxilite already respects on D1 apply here too.

3Write the Durable Object

GraphMemory opens the store once, in blockConcurrencyWhile, so the schema exists before the first request. Opening is idempotent: the first time it creates the tables, and afterwards it finds them. The public methods become RPC methods the Worker can call directly.

src/index.ts: the object 
import { DurableObject } from "cloudflare:workers";
import { D1Store } from "@oxilite/d1";
import wasm from "@oxilite/d1/oxilite.wasm";
import { durableObjectDatabase } from "./do-sql";

type Store = Awaited<ReturnType<typeof D1Store.open>>;

interface Env {
  MEMORY: DurableObjectNamespace<GraphMemory>;
}

export class GraphMemory extends DurableObject<Env> {
  private store!: Store;

  constructor(ctx: DurableObjectState, env: Env) {
    super(ctx, env);
    ctx.blockConcurrencyWhile(async () => {
      this.store = await D1Store.open(durableObjectDatabase(ctx.storage), { wasm });
    });
  }

  /** Adds facts, in Turtle, to one named graph: the provenance of the facts. */
  async remember(turtle: string, source: string): Promise<void> {
    await this.store.load(turtle, {
      format: "text/turtle",
      to_graph_name: { termType: "NamedNode", value: source },
    });
  }

  /** SPARQL JSON results; `reasoning` applies RDFS or OWL QL entailment at query time. */
  async query(sparql: string, reasoning?: "rdfs" | "owl-ql"): Promise<string> {
    if (!reasoning) return this.store.queryJson(sparql);
    return (await this.store.query(sparql, {
      reasoning, results_format: "application/sparql-results+json",
    })) as string;
  }

  async update(sparql: string): Promise<void> {
    await this.store.update(sparql);      // one transaction
  }

  explain(sparql: string): string {
    return this.store.explain(sparql);    // the SQL, the join order, warnings
  }
}

4Route requests to the right agent

The Worker is a thin router. It turns the agent name in the path into a Durable Object id and calls the object's methods over RPC. Requests for ada reach Ada's graph wherever in the world they arrive.

src/index.ts: the Worker 
export default {
  async fetch(req: Request, env: Env): Promise<Response> {
    const url = new URL(req.url);
    const m = url.pathname.match(/^\/agents\/([\w-]+)\/(remember|sparql|update|explain)$/);
    if (!m) return new Response("not found", { status: 404 });
    const [, agent, action] = m;
    const memory = env.MEMORY.get(env.MEMORY.idFromName(agent));
    try {
      switch (action) {
        case "remember":
          await memory.remember(await req.text(), url.searchParams.get("source") ?? `urn:agent:${agent}:inbox`);
          return new Response(null, { status: 204 });
        case "sparql": {
          const reasoning = url.searchParams.get("reasoning");
          if (reasoning && reasoning !== "rdfs" && reasoning !== "owl-ql") throw new Error("reasoning must be rdfs or owl-ql");
          return new Response(await memory.query(await req.text(), reasoning ?? undefined), {
            headers: { "content-type": "application/sparql-results+json" },
          });
        }
        case "update":
          await memory.update(await req.text());
          return new Response(null, { status: 204 });
        default:
          return new Response(await memory.explain(url.searchParams.get("query") ?? ""));
      }
    } catch (e) {
      return new Response(e instanceof Error ? e.message : String(e), { status: 400 });
    }
  },
};

5Try it

Run npx wrangler dev, then teach the agent a few facts. Each call names its source, which becomes the named graph that holds those facts.

# from a chat with the user
curl -X POST 'localhost:8787/agents/ada/remember?source=urn:chat:1' --data-binary '
  @prefix ex: <http://example.com/> .
  ex:maria ex:worksAt ex:acme ; ex:prefers ex:email .
  ex:acme ex:partOf ex:globex .
  ex:globex ex:headquarteredIn ex:berlin .'

# from a CRM export
curl -X POST 'localhost:8787/agents/ada/remember?source=urn:crm:export' --data-binary '
  @prefix ex: <http://example.com/> .
  ex:berlin ex:timezone "Europe/Berlin" .'

A multi-hop question

Which time zone should the meeting with Maria use? The property path ex:partOf*/ex:headquarteredIn climbs the company hierarchy to any depth, and the answer combines facts from two sources:

curl -X POST localhost:8787/agents/ada/sparql --data-binary '
  PREFIX ex: <http://example.com/>
  SELECT ?tz WHERE {
    GRAPH ?g1 { ex:maria ex:worksAt ?org }
    GRAPH ?g2 { ?org ex:partOf*/ex:headquarteredIn ?city }
    GRAPH ?g3 { ?city ex:timezone ?tz }
  }'
# → ?tz = "Europe/Berlin"

The whole query, recursion included, compiles to one SQL statement. On a Durable Object that statement runs in-process.

Where did a fact come from?

PREFIX ex: <http://example.com/>
SELECT ?p ?o ?source WHERE { GRAPH ?source { ex:maria ?p ?o } }
# → worksAt acme   urn:chat:1
#   prefers email  urn:chat:1

Changing its mind

Maria says she now prefers chat. One SPARQL update removes the old preference, from whichever source it came from, and records the new one with its own provenance. It runs as a single transaction, so a crash can't leave Maria with two preferences or none.

curl -X POST localhost:8787/agents/ada/update --data-binary '
  PREFIX ex: <http://example.com/>
  DELETE { GRAPH ?g { ex:maria ex:prefers ?old } }
  INSERT { GRAPH <urn:chat:2> { ex:maria ex:prefers ex:chat } }
  WHERE  { GRAPH ?g { ex:maria ex:prefers ?old } }'

And a second agent, bob, sees none of it: /agents/bob/sparql reaches a different object with a different database.

Giving the graph to a model

To let a model use this memory, expose two tools that map onto the routes above. Put the tool definitions in whatever format your model API expects. The important decisions are in the descriptions and in what each tool is allowed to do.

[
  {
    "name": "remember",
    "description": "Store durable facts about the user or their world as Turtle triples. Use the prefix ex: <http://example.com/>. Only store facts the user stated or that came from a trusted tool.",
    "input_schema": {
      "type": "object",
      "properties": {
        "turtle": { "type": "string" },
        "source": { "type": "string", "description": "Where the facts came from, e.g. urn:chat:42" }
      },
      "required": ["turtle", "source"]
    }
  },
  {
    "name": "recall",
    "description": "Answer a question from memory with a read-only SPARQL SELECT or ASK query. Use GRAPH ?source to see where facts came from.",
    "input_schema": {
      "type": "object",
      "properties": { "query": { "type": "string" } },
      "required": ["query"]
    }
  }
]
  • recall can't write. It goes to queryJson, which parses a SPARQL query. An INSERT or DELETE is rejected as a syntax error, so a confused model can't damage its memory while reading.
  • Revisions go through your code. Keep the /update route for logic you control, such as "replace this preference", rather than handing the model arbitrary updates.
  • Errors help the model fix its query. Parse errors come back as text. Returning them as the tool result usually lets the model correct its query on the next try.
  • Provenance is automatic. Because every remember call names a source, the model can weigh "the user said" against "a web page said" when facts disagree.

What to know before production

  • Test status. D1 is oxilite's tested Cloudflare target: the W3C SPARQL suites run on it. The Durable Object adapter in this article is an example, with its own end-to-end test on Miniflare's SQLite-backed Durable Objects (node test.mjs). It isn't yet part of the full W3C runs.
  • Size. A Durable Object's storage has a per-object size limit, so plan for one graph per agent or user, not one giant graph. For a large shared knowledge base, use D1 and keep per-agent memory in Durable Objects.
  • Statistics. After a large import, call store.optimize() so the planner knows which predicates are rare. It reads the whole table, so run it occasionally, not on every write.
  • Reasoning. Add ?reasoning=rdfs to a query and the engine applies the ontology at query time, just as on D1. Store ex:Employee rdfs:subClassOf ex:Person once, and a question about people also finds Maria, who was only ever recorded as an employee. The example's test checks exactly that.

The takeaway. A Durable Object gives each agent a private, transactional SQLite database. oxilite turns that database into a knowledge graph the agent can query across relationships, trace back to sources, and update as facts change. The adapter between the two is about 30 lines, because oxilite's core was built to run on any SQLite it's given.
