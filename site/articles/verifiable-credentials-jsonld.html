Verifiable Credentials and JSON-LD, in SQLite

Keep every credential exactly as it was issued, and still ask your wallet questions like “which valid degrees did this university issue?” with SPARQL. It all lives in one SQLite file, on Node.js, Rust and Cloudflare D1.

A walkthrough · Every step is checked by examples/verifiable-credentials, on @oxilite/node and on D1

Two views of one credential

A Verifiable Credential is a JSON-LD document. Wallets, issuers and verifiers need it in two ways at once:

  • As JSON, exactly as issued. You present it, forward it, archive it and verify its proof. A copy rebuilt from a database is not the credential that was signed.
  • As data. “All credentials about this subject.” “Degrees still valid today.” “Which credential says this person is a chess master?” Those are graph questions.

oxilite keeps both. The JSON goes into a table under the credential's id, byte for byte. Its RDF goes into a named graph with the same IRI, next to your other data, and SPARQL can query it. The issuer, subject, types and validity window are also copied into indexed columns, so common lookups need no SPARQL at all.

Setup

npm install @oxilite/node              # Node.js; @oxilite/d1 for Workers
cargo add oxilite --features vc        # Rust; "jsonld" without credentials
import { Store } from "@oxilite/node";

const store = new Store("wallet.sqlite");
const vcs = store.credentials();

1Store a credential

Take the degree credential from the VC Data Model 2.0 examples, with a Data Integrity proof:

{
  "@context": ["https://www.w3.org/ns/credentials/v2", "https://www.w3.org/ns/credentials/examples/v2"],
  "id": "http://university.example/credentials/3732",
  "type": ["VerifiableCredential", "ExampleDegreeCredential"],
  "issuer": "https://university.example/issuers/565049",
  "validFrom": "2010-01-01T00:00:00Z", "validUntil": "2040-01-01T00:00:00Z",
  "credentialSubject": {
    "id": "did:example:ebfeb1f712ebc6f1c276e12ec21",
    "degree": { "type": "ExampleBachelorDegree", "name": "Bachelor of Science and Arts" }
  },
  "proof": { "type": "DataIntegrityProof", "cryptosuite": "eddsa-rdfc-2022", "proofValue": "z58DAdFfa9…", … }
}
const id = vcs.put(degreeJson);
// "http://university.example/credentials/3732"

put does four things, all in one atomic write: one transaction natively, one batch() on D1.

  • Checks the structure. The first @context selects VCDM 1.1 or 2.0. The ssi-vc crate then checks the context order, the VerifiableCredential type, the issuer and the subject.
  • Stores the JSON. The key is the credential's id.
  • Converts it to RDF. The json-ld crate does the conversion into the graph <id>. The W3C credential, security and DID contexts are bundled, so nothing is downloaded, on D1 either.
  • Indexes the metadata: issuer, subject, types and the validity window.

Storing a credential with the same id again replaces it and clears exactly its old triples.

2See what was stored

const stored = vcs.get(id);
stored.json === degreeJson        // true: the exact bytes, e.g. for verification
stored.profile                    // "vc2"
stored.issuer                     // "https://university.example/issuers/565049"
stored.validUntil                 // Date 2040-01-01T00:00:00.000Z
vcs.documents.graphs(id)          // [BlankNode (the proof graph), NamedNode <…/3732>]

The credential's graph holds its claims. JSON-LD declares proof as a graph container, so the proof sits in a graph of its own. That graph is owned by the credential and linked from it with sec:proof. Your claim queries therefore never trip over signatures, and removing the credential removes the proof as well:

<…/3732> rdf:type          cred:VerifiableCredential, ex:ExampleDegreeCredential ;
         cred:issuer       <https://university.example/issuers/565049> ;
         cred:validFrom    "2010-01-01T00:00:00Z"^^xsd:dateTime ;
         cred:credentialSubject <did:example:ebfeb1f712ebc6f1c276e12ec21> ;
         sec:proof         _:proof .          # the proof triples are in graph _:proof

3Ask questions with SPARQL

Each credential is its own graph, so GRAPH ?cred tells you which credential says something. That makes provenance free:

const rows = store.query(`
  SELECT ?cred ?name WHERE {
    GRAPH ?cred { ?s <https://www.w3.org/ns/credentials/examples#degree> ?d .
                  ?d <https://schema.org/name> ?name }
  }`);
// [{ cred: <http://university.example/credentials/3732>, name: "Bachelor of Science and Arts" }]
vcs.documents.documentForGraph(rows[0].get("cred")).json   // back to the credential itself

4Store a presentation

const { key, credentials } = vcs.putPresentation(presentationJson);
// key: "urn:uuid:3978344f-…", credentials: ["urn:uuid:vc-a", "urn:uuid:vc-b"]

The presentation is stored as it is. Each credential it embeds is also stored as a credential of its own, in the same atomic write, so you can find, query and remove it separately. The presentation's graph still contains its embedded copies. To look only at credentials, keep the named graphs:

SELECT ?cred WHERE {
  GRAPH ?cred { ?s ex:achievement "Go master" }
  FILTER(isIRI(?cred))               # skips the presentation's embedded copy
}                                    # → <urn:uuid:vc-b>

5Look up credentials without SPARQL

vcs.find({ issuer: "did:example:academy", validAt: new Date() });
vcs.find({ subject: "did:example:ebfeb1f712ebc6f1c276e12ec21", type: "ExampleDegreeCredential" });

find reads the metadata columns: one SQL statement with keyset paging (after, limit). validAt reads validFrom/validUntil from VCDM 2.0 credentials and issuanceDate/expirationDate from 1.1 credentials. On D1 every index entry is a billed write, so you choose which metadata indexes exist: store.credentials({ indexes: { subject: false } }).

6Any JSON-LD, with your own contexts

Credentials are one profile. store.jsonld() stores any JSON-LD document the same way. Contexts are loaded offline. You can register them on the handle, or persist them in the store once, which makes them work from every process and on D1:

const docs = store.jsonld();
docs.putContext("https://example.org/contexts/recipe.jsonld",
  { "@context": { "@vocab": "https://schema.org/", ingredients: "recipeIngredient" } });
docs.put(`{"@context": "https://example.org/contexts/recipe.jsonld",
          "@id": "https://example.org/recipes/pancakes", "@type": "Recipe",
          "name": "Pancakes", "ingredients": ["flour", "milk", "eggs"]}`);
// GRAPH <https://example.org/recipes/pancakes> now holds 3 schema:recipeIngredient triples

An unknown context fails with JsonLdError code loading remote context failed, and nothing is written. On Node you can opt in to downloading with network: true, and add cacheFetched: true to persist what was downloaded. The conversion passes 450 tests of the W3C JSON-LD 1.1 toRdf suite.

7Choose keys and graphs

OptionValuesDefault
key"id", { pointer: "/credentialSubject/id" }, "contentHash", "explicit""id"
onMissingKey"reject", "contentHash" (urn:oxilite:doc:sha256:…)credentials: "contentHash"; documents: "reject"
graph"key", { template: "https://ex.org/holders/{key}" }, { fixed: iri }, "default""key"

With a graph per document, a replace or remove clears the document's graph without reading it first. With a shared graph (fixed or default), the previous version is read back and exactly its triples are removed. VCDM 2.0 makes id optional. Credentials without one get a content-hash key, so storing the same one twice keeps a single copy.

8Keep graphs honest

The stored JSON is the source of truth, and the graphs are derived from it. SPARQL UPDATE can still edit them. If it does, check() reports the drift and rebuild() regenerates the graph from the JSON:

store.update(`DELETE WHERE { GRAPH <${id}> { ?d <https://schema.org/name> ?n } }`);
vcs.documents.check();       // [{ key: id, missing: 1, extra: 0 }]
vcs.documents.rebuild(id);   // true, and check() is [] again

The same in Rust and on D1

let store = oxilite::store::Store::open("wallet.sqlite")?;
let vcs = store.credentials()?;
let id = vcs.put_credential(&degree_json)?;
let valid = vcs.find_credentials(&CredentialFilter { issuer: Some(issuer), valid_at: Some(now), ..Default::default() })?;
// Cloudflare Worker with @oxilite/d1: same API, asynchronous; every write is one D1 batch
const store = await D1Store.open(env.DB, { wasm });
const vcs = store.credentials();
await vcs.put(credential);
const valid = await vcs.find({ issuer, validAt: new Date() });

For migrations, npx oxilite-d1 schema --jsonld adds the three JSON-LD tables to the schema. JSON-LD and credential support adds about 0.4 MB (gzipped) to the WebAssembly module, which stays well within the Workers limits.

Limits to know

  • Proofs are not verified. Storing a credential says nothing about whether it is valid. Verify the stored JSON with a library such as ssi, then store it or act on it.
  • One batch per document. Large documents are written in chunks inside one atomic batch. A document that needs more statements than D1 allows in one batch is refused (document-too-large) rather than split.
  • No network in Workers. Persist the contexts your documents use with putContext. The W3C credential contexts are already included.
  • Not included: status-list revocation checks, JSON-LD framing or compaction on read (you get the original JSON), and enveloped (JOSE/COSE) credentials inside presentations.

The takeaway. Each credential is stored twice over: the exact JSON under its id, and its claims as a named graph you can query. Graph queries tell you which credential says what, metadata lookups answer the everyday questions, and nothing needs the network, even on Cloudflare D1.
