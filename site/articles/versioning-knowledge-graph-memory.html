Versioning · Overview · Use cases

A knowledge graph with a memory

Most databases hold the present and forget the rest. For a knowledge graph that is a real limit. The questions that matter are often about the past: what the agent believed, who changed a fact, which import broke the ontology. oxilite can now remember, inside the same SQLite file or D1 database, and answer those questions with SPARQL and Datalog.

An overview · For the step-by-step tour see Time travel for your knowledge graph; for the numbers, How much does versioning slow oxilite down?; for every option, the reference

What versioning records

Versioning is chosen per store, at one of three levels. A store without it is exactly the store it was before: the same tables and the same SQL, which a golden test holds to the last release, and the same bill.

LevelWhat the store remembers
off (default)Nothing: the present only.
stampedA store clock. Every write is a tick with a time, an author and a message, and every quad records the tick that added it.
logEverything. An immutable change log of every addition and removal, so any past version can be queried and any two versions compared.

A write is a commit: a SPARQL update, a load batch, a Cypher write or a JSON-LD document. Triggers under the quad table record it, so no write path can skip the history, and writes that change nothing record nothing. The log cannot be edited. The database itself refuses to update or delete recorded history, and the only exception is an audited purge for erasure requests.

What you can ask

  • Any query, at any version. as_of: "HEAD~3", "#42" or "@2026-09-01T12:00:00Z" runs a SPARQL query against the store as it was, with paths, OPTIONAL and GRAPH included, still as one SQL statement. On the command line it is --as-of, and on the HTTP endpoint ?version=.
  • Two versions in one query. SERVICE <oxilite:version/HEAD~1> { … } reads a group at another version, so "what changed and from what" is a single query.
  • Rules over the past. A Datalog program with @version "HEAD~1" . runs its recursion on that version. A single atom can read another version with at "HEAD~1", or the version of a commit with at ?c.
  • Property graphs too. Cypher takes the same asOf option.
  • History as a graph. GRAPH <oxilite:history> describes every commit with PROV-O (time, author, message, the commit before) and every change as a triple term. "Who revoked Alice's admin role" is one SPARQL query. Datalog reads the same history as commit, added and removed relations.
  • The history itself. history() lists commits with author, message and counts. diff(from, to) gives the net change between two versions. changes(since) is a change feed. The CLI prints diffs and changes as RDF Patch.
  • Levels on demand. Raise a live store to log and its current state becomes the genesis commit. Lower it and the history freezes but stays readable. Raise it again and the gap becomes one commit. Nothing is deleted without allow_loss.

It works the same on every surface: Rust, @oxilite/node, @oxilite/d1 in a Worker, the CLI and the SPARQL endpoint. On D1 a batch is a commit, and level changes ship as migrations.

The use cases

1. Agent memory you can audit and roll back

An AI agent that stores what it learns in a knowledge graph needs more than the latest facts. When it gives a wrong answer, you want to know what it believed at that moment, which tool wrote the belief, and how to get rid of it. Give each tool its own author, and every belief is attributed:

await store.withCommit({ author: "web-search", message: `ingest ${url}` }, (s) => s.update(facts));

// What did the agent believe when it answered at 14:02?
const then = await store.query(question, { as_of: "@2026-09-25T14:02:00Z" });

// What did that ingestion change?
const changed = await store.diff("#41", "#42");

Level: log. The diff of a bad commit is exactly the set of triples to revert.

2. Curated knowledge graphs and ontologies

When several people, or people and scripts, edit an ontology or a reference graph, reviewers need to see what a change did, not just its message. oxilite versioning log shows who changed what and when, with counts. oxilite versioning diff HEAD~1 shows the exact triples. A SERVICE <oxilite:version/…> query turns a review question into a query, such as "which classes lost their rdfs:label in the last ten commits".

Level: log. Branches and merge, the natural next step, are planned. See the end of this article.

3. Audit: what did we know, and when?

A decision made on the data should be explainable later, against the data as it was, not as it is now. With log, "what did we know at the time of the decision" is a query with as_of set to the decision's timestamp, not a backup to restore. When a person asks to be forgotten, purge removes their triples from the present and from every past version. It records that a purge happened, by whom and why, without recording what was removed.

4. Change feeds: search indexes, caches, exports

Many systems keep a derived copy of the graph: a search index, a cache, an analytics export. They need to know what changed since the last sync. At level stamped every quad carries the tick that added it, and the store's clock only moves forward. So "everything added since tick 1,204" is one call, changes(1204), and it adds no rows per triple on D1. At log the same feed includes removals.

oxilite versioning changes -l kb.sqlite --since 1204      # A / D lines, grouped by tick

5. Reproducible analysis

A report, a model's training set or a benchmark built from a live graph changes when the graph does. Record the tick it was built from and anyone can rebuild it exactly: the same query with as_of: "#1204" returns the same answer next month.

6. Debugging data pipelines

When something is wrong in the graph, the question is which import did it. The history names every batch, and changes shows what each one did. A Datalog rule with at ?c shows the value of a fact at every commit, so you can see exactly when a derived fact first appeared or disappeared.

Which level for which job

Use caseLevelWhy
Change feeds, incremental export, "what's new"stampedAdditions with their tick and author, no extra rows per triple
Agent memory, curated graphs, auditlogPast versions, removals, diffs, attribution
The same, queried oftenlog + as-of indexSelective queries on the past near the speed of the present
Caches, derived storesoffNothing to remember, nothing to pay

What it costs

In brief:

  • Current-state queries cost the same at every level.
  • Writes: a store clock adds no rows per triple on D1. A full log adds about 42 %, and about 83 % with the as-of index.
  • Reading the past costs about 3× the present for subject lookups. With the as-of index, selective queries cost 1–3.5×. Aggregating a predicate's whole history stays much slower.

The full measurements, and why they come out that way, are in How much does versioning slow oxilite down?.

Getting started

# a new store that keeps its history
oxilite update -l kb.sqlite --versioning log --author ada -m "seed" -u 'INSERT DATA { … }'

# an existing store: raise its level (its current state becomes the genesis commit)
oxilite versioning set -l kb.sqlite log

# a D1 database: the same change as a migration
npx oxilite-d1 versioning-migration --from off --to log > migrations/0002_versioning.sql

Not yet

  • Branches and merge. Prepare changes apart, review them, validate them against SHACL, then merge. Planned, and gated on the read-latency work described in the benchmark article.
  • Push and pull between stores, such as a laptop and D1.

The takeaway. Versioning turns "what is true" into "what was true, when, and who said so", for agents, curators, auditors and the systems that copy your graph. Opt in per store. If you don't, nothing changes.
