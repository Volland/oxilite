N3 · Rules · Reasoning · Guide

Notation3 rules over a SQLite knowledge graph

Notation3 is the rule language of the Semantic Web stack: rules are triples about triples, { … } => { … }. oxilite now runs N3 with eyeron, an EYE-compatible reasoner written in Rust. You can ask what follows from your graph without writing anything, or store the conclusions as inferences that SPARQL, Cypher and Datalog read like any other.

A guide · Every rule and result on this page comes from the test suite (n3.rs) or from the oxilite command line

Where N3 fits

oxilite already reasons three ways: RDFS and OWL QL rewriting at query time, OWL 2 RL materialization, and its own Datalog. N3 adds what those cannot say:

  • Rules as data. A rule is a triple between two formulas, so a rule can conclude another rule.
  • Builtins for math, strings, lists, time and lookups: math:sum, string:matches, list:member, time:localTime, and many more.
  • Scoped negation and aggregates: log:notIncludes, log:collectAllIn, log:forAllIn.
  • Backward rules (<=), queries (log:query) and inference fuses: { … } => false stops the run when the data matches something forbidden.
  • Proofs: every conclusion can come with the rule, the bindings and the facts it used.

Setup

cargo add oxilite --features n3          # Rust
cargo install oxilite-cli                # the command line has N3 built in

eyeron is a normal crates.io dependency, built without its HTTP client, so a rule never fetches anything from the web.

1. Ask what follows

Start with a small family graph and one rule:

# kg.ttl
@prefix ex: <http://example.org/> .
ex:ada ex:parent ex:bob . ex:bob ex:parent ex:cy .
ex:ada a ex:Person ; ex:name "Ada" ; ex:email "ada@example.org" .
ex:bob a ex:Person ; ex:name "Bob" .
ex:cy  a ex:Person .

# grand.n3
@prefix ex: <http://example.org/> .
{ ?x ex:parent ?y . ?y ex:parent ?z } => { ?x ex:grandparent ?z } .
$ oxilite load -l kg.db -f kg.ttl
$ oxilite n3 -l kg.db -f grand.n3
<http://example.org/ada> <http://example.org/grandparent> <http://example.org/cy> .
1 conclusion(s) from 2 statement(s)

from 2 statement(s) is the first thing to notice. The rule only reads ex:parent, so only the two parent statements were loaded, not the names, emails or types. oxilite collects the predicates of every rule body and reads just those, in one request. A rule with a variable predicate ({ ?s ?p ?o } => …) reads the whole scope, and so does --no-prune.

The same from Rust:

let r = store.n3_reason(rules)?;    // nothing is written
for t in &r.derived { println!("{t}"); }
assert!(r.complete);

2. Keep the proof

Add --proof (or Options { proof: true, .. }) and eyeron explains each conclusion: the rule, the bindings and the facts it used.

$ oxilite n3 -l kg.db -f grand.n3 --proof
...
{ ex:ada ex:grandparent ex:cy . }
  pe:rule
    { { ?x ex:parent ?y . ?y ex:parent ?z . } => { ?x ex:grandparent ?z . } . };
  pe:binding
    [ pe:var "x"; pe:value ex:ada ],
    [ pe:var "y"; pe:value ex:bob ],
    [ pe:var "z"; pe:value ex:cy ];
  pe:uses
    { ex:ada ex:parent ex:bob . },
    { ex:bob ex:parent ex:cy . }.

The proof is N3 too, so you can store it, query it, or give it to another reasoner to check.

3. Store the conclusions

--materialize writes the conclusions into oxilite's inference table, under a producer name (n3 by default):

$ oxilite n3 -l kg.db -f grand.n3 --materialize
1 inferred triple(s) from 2 statement(s) (producer n3)

$ oxilite query -l kg.db --inferred -q 'SELECT ?z WHERE { <http://example.org/ada> <http://example.org/grandparent> ?z }'

Inferences sit beside the asserted data, not in it. A query sees them only with include_inferred (--inferred), and store.inference_producers(&quad) tells you that n3 derived one. Each run replaces its producer's earlier conclusions in one atomic request, so the stored set always matches the store as it is now. Delete ex:bob ex:parent ex:cy, materialize again, and the grandparent triple is gone. Other producers are not touched: OWL 2 RL (owl2rl), Datalog programs and other N3 rule sets each keep their own conclusions.

Give each rule set its own producer, so they can be refreshed independently:

store.n3_materialize_with(family_rules, &Options { producer: "family".into(), ..Default::default() })?;
store.n3_materialize_with(org_rules,    &Options { producer: "org".into(),    ..Default::default() })?;

4. Rules on top of rules

With include_inferred, a run also reads the conclusions of other producers, so one rule set can build on another's output, or on OWL 2 RL's. It never reads its own: a conclusion whose premise was deleted can't keep itself alive by being read back in.

store.materialize()?;                                         // OWL 2 RL, producer owl2rl
store.n3_materialize_with(rules, &Options { include_inferred: true, ..Default::default() })?;

5. Negation, aggregates and the clock

Scoped negation as failure asks whether something is not in the data. Here, a person without an email address is unreachable:

@prefix ex: <http://example.org/> .
@prefix log: <http://www.w3.org/2000/10/swap/log#> .
{ ?p a ex:Person . ?SCOPE log:notIncludes { ?p ex:email ?e } } => { ?p a ex:Unreachable } .
$ oxilite n3 -l kg.db -f unreachable.n3
<http://example.org/bob> <http://www.w3.org/1999/02/22-rdf-syntax-ns#type> <http://example.org/Unreachable> .
<http://example.org/cy> <http://www.w3.org/1999/02/22-rdf-syntax-ns#type> <http://example.org/Unreachable> .

Rules like this are non-monotonic: adding an email to Bob takes back a conclusion. Some reasoners refuse to store them. oxilite can, because each materialization recomputes its producer from scratch. r.info.monotonicity still tells you which kind of rule set you have.

time:localTime reads the clock. Pin it with --now MILLIS or Options::now, so the same rules over the same data give the same answer, which tests and audits need.

6. Fuses: rules that forbid

A rule whose conclusion is false is a constraint. When the data matches it, reasoning stops and says why:

$ cat fuse.n3
{ ?x a ex:Dog . ?x a ex:Cat } => false .

$ oxilite n3 -l kg.db -f fuse.n3 --materialize
error: N3 inference fuse fired: # Inference fuse triggered.
# Fired rule:
#   { ?x a ex:Dog . ?x a ex:Cat . } => false .
# Matched instance:
#   { ex:rex a ex:Dog . ex:rex a ex:Cat . } => false .

n3_reason reports the fuse in r.fuse. n3_materialize fails before writing anything, so a rule set whose constraints are violated never stores half its conclusions.

7. Scope, limits and what can't be stored

OptionCLIEffect
graphs--graph GReason over chosen graphs only. By default every graph but the system graphs is read, merged.
include_inferred--inferredAlso read other producers' inferences.
prune--no-pruneTurn predicate pruning off.
producer--producerThe name stored conclusions are attributed to.
limits--max-iterationseyeron's step limits. A run they cut short is complete: false. Materialization refuses it, so a partial fixpoint is never stored.
now, proof--now, --proofPin the clock; return the proof.

N3 can conclude things RDF can't hold, such as a triple whose subject is a literal ("Ada" ex:nameOf ex:ada) or one whose object is a list. Those come back as N3 text in r.unstorable and are never written. Blank nodes a rule invents keep eyeron's deterministic labels, so a rerun reproduces the same node.

On Cloudflare D1

A run is one read request for the pruned scope, reasoning in memory, and, when materializing, one atomic write. That works the same way over D1, so AsyncStore::n3_reason and n3_materialize run there unchanged. Keep the scope small (one graph, a pruned rule set): the whole input is held in memory while eyeron reasons.

The takeaway. Write the rule once in N3. Ask what follows from it, with a proof if you want one, or store what follows as inferences your queries can opt into. Pruning keeps the read small, fuses keep bad data from being half-reasoned over, and each rule set's conclusions can be refreshed or dropped on their own.
