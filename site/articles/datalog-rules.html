Datalog · Recursion · Rules

Rules your SPARQL can't write

SPARQL's only recursion is a property path: one predicate, a fixed regular expression, no way to join another relation or filter part-way through. oxilite 0.3.0 adds Datalog over the same quads — and compiles it to a single SQL statement.

A walkthrough · Every program on this page is taken from the test suite: basics.rs, recursion.rs and datalog.test.ts

The ceiling

You can ask SPARQL for everyone Ada is an ancestor of:

SELECT ?who WHERE { ex:ada ex:parent+ ?who }

That is the last recursive question SPARQL will answer for you. A property path walks one predicate along a fixed regular expression. It cannot join a second relation between two steps, cannot drop a branch that fails a test, cannot say "reachable but not blocked", and cannot count what it found on the way. The moment your question needs any of that, you leave the query language: you write a loop in the host language and pay a round trip per hop.

Datalog is the standard answer, and it has been for forty years. A rule is an implication; rules may refer to themselves; the engine finds the fixpoint. oxilite 0.3.0 ships that as oxilite-datalog, over the same quads, the same term encoding and the same backends as SPARQL and Cypher.

The language

It is RDF-native, spelled like Turtle and SPARQL, so nothing new to learn about terms:

FormMeans
ex:parent(?x, ?y)the triple pattern ?x ex:parent ?y
ex:Person(?x)?x rdf:type ex:Person
triple(?s, ?p, ?o)any triple in the default graph — predicate variable included
triple(?s, ?p, ?o, ?g)any quad
p(?x, ?y)a relation defined by rules
not p(?x, ?y)stratified negation
?a >= 18, ?a * 2 < 40constraints, in SPARQL's expression language
n(?x, COUNT(?y)) :- …aggregation, grouped by the head's other arguments
?- p(?x, ?y).the goal: what the program returns

Variables are ?x, _ is anonymous, prefixes come from @prefix, literals carry ^^ datatypes and @ language tags, and % or # starts a comment.

Setup

npm install @oxilite/node              # Node.js
cargo add oxilite --features datalog   # Rust

The data for every example below is a parent chain and a few ages:

# ada → bob → cy → dee
ex:ada ex:parent ex:bob . ex:bob ex:parent ex:cy . ex:cy ex:parent ex:dee .
ex:ada ex:age 42 . ex:bob ex:age 17 . ex:cy ex:age 71 . ex:dee ex:age 8 .
ex:ada a ex:Person . ex:bob a ex:Person . ex:cy a ex:Person . ex:dee a ex:Person .

1Recursion, with a goal

const r = store.datalog(`
  @prefix ex: <http://example.org/> .

  anc(?x, ?y) :- ex:parent(?x, ?y).
  anc(?x, ?z) :- ex:parent(?x, ?y), anc(?y, ?z).

  ?- anc(ex:ada, ?who).`);

r.columns          // ["who"]
r.rows.map(row => row[0].value)
// http://example.org/bob, .../cy, .../dee

Two rules: the base case and the recursive step. The goal fixes Ada and projects the other column. Results come back as RDF/JS terms, and r.records gives the same rows keyed by variable name.

So far a property path would have done. Now the things it cannot.

2Join and filter mid-recursion

A constraint is an ordinary body item, in SPARQL's expression language:

adult(?p) :- ex:age(?p, ?a), ?a >= 18.
?- adult(?p).
// ex:ada, ex:cy

young(?p) :- ex:age(?p, ?a), ?a * 2 < 40.
?- young(?p).
// ex:bob, ex:dee

Arithmetic is evaluated on the bound value, not on a string. Drop either rule into the recursive anc definition and the filter applies at every step of the walk — the thing a property path has no syntax for.

3Negation, stratified

anc(?x, ?y) :- ex:parent(?x, ?y).
anc(?x, ?z) :- ex:parent(?x, ?y), anc(?y, ?z).
root(?x)    :- ex:Person(?x), not anc(_, ?x).
?- root(?x).
// ex:ada — the only person with nobody above them

not ranges over a relation the program itself derived recursively. That is stratified negation: anc is computed to completion first, then root is evaluated against it. The compiler works out the strata; you never order the rules yourself.

Ask for something that cannot be stratified and you get a rule diagnostic, not a runtime surprise:

p(?x) :- ex:Person(?x), not p(?x).
// error: … not stratified … naming the cycle through p

4Aggregation

n(?x, COUNT(?y)) :- anc(?x, ?y).
?- n(?x, ?c).
// ex:ada 3, ex:bob 2, ex:cy 1

An aggregate in the head groups by the head's other arguments. Counting the results of a recursive relation in the query language is, again, not something SPARQL's property paths reach.

5Quantify over the predicate

uses(?p) :- triple(ex:ada, ?p, _).
?- uses(?p).
// ex:parent, ex:age, rdf:type

The built-in triple/3 and triple/4 forms put a variable in the predicate — or the graph — position, which is how you write rules about the shape of your data rather than about one vocabulary.

One statement, one round trip

The interesting part is what this compiles to. Every relation — stored or derived — is a set of rows of tagged 64-bit term ids, the same encoding the SPARQL compiler uses, so a derived predicate composes with a triple pattern with no conversion at all. Then:

  • a non-recursive predicate becomes a plain common table expression;
  • a linear recursive component becomes one WITH RECURSIVE member;
  • a mutually recursive component becomes one member carrying a discriminant column.

The whole program is one SQL statement, which means one round trip — the property that makes oxilite work on a remote database like D1 at all. Mutual recursion is genuinely mutual:

even(?x) :- ex:Zero(?x).
even(?x) :- ex:succ(?y, ?x), odd(?y).
odd(?x)  :- ex:succ(?y, ?x), even(?y).
?- even(?x).

store.explainDatalog(…) reports the strata and the strategy chosen for each component, and datalog_sql() hands you the SQL itself.

The restrictions are the classical ones

This is the part worth dwelling on. SQLite's recursive-CTE rules look arbitrary until you line them up with Datalog theory, and then they are the same conditions:

  • one self-reference per recursive term → rules must be linear;
  • no self-reference under NOT EXISTS → negation must be stratified.

So the compiler checks them before any SQL exists and reports them as rule diagnostics. An unsafe rule names the unbound variable:

p(?x, ?y) :- ex:Person(?x).
// error: … ?y … — a head variable no body atom binds

And a non-linear rule does not merely get refused — the diagnostic shows you the linear rewrite:

path(?x, ?y) :- ex:succ(?x, ?y).
path(?x, ?z) :- path(?x, ?y), path(?y, ?z).   // two recursive atoms
// error: … non-linear … :- e(?x,?y), p(?y,?z)

Take the rewrite and the program runs as a single statement again. If you would rather keep the non-linear form, it is evaluated instead by iterating to a fixpoint in a work table — one request per round, driven by the same step machine as everything else, so it still runs on D1. r.rounds reports what each iterated component took (it is empty when nothing needed iteration), and maxIterations bounds it. Because those rounds write, a non-linear program needs a writable store.

Rules that become data

A program can store its conclusions instead of returning them:

const stats = store.datalogMaterialize(`
  @prefix ex: <http://example.org/> .
  ex:ancestor(?x, ?y) :- ex:parent(?x, ?y).
  ex:ancestor(?x, ?z) :- ex:parent(?x, ?y), ex:ancestor(?y, ?z).`);

stats  // { relations: 1, inferred: 6 }

store.query("SELECT ?y WHERE { ex:ada ex:ancestor ?y }");
// [] — asserted data is untouched

store.query("SELECT ?y WHERE { ex:ada ex:ancestor ?y }", { include_inferred: true });
// 3 rows

Note the head is an IRI here, ex:ancestor, because the conclusions have to be triples. They go into quads_inf — the same table OWL 2 RL materialization writes — so your rules extend the reasoner rather than running beside it, and SPARQL and Cypher both see them under include_inferred. The two share one inference set: running either replaces it. A one-argument head such as ex:Adult(?p) is stored as an rdf:type triple.

Everywhere oxilite runs

// Rust
let r = store.datalog(program)?;
let plan = store.explain_datalog(program)?;
let stats = store.datalog_materialize(program)?;
# Command line
oxilite datalog -l db.sqlite -f rules.dl
oxilite datalog -l db.sqlite -f rules.dl --explain
oxilite datalog -l db.sqlite -f rules.dl --materialize
// Cloudflare Worker with @oxilite/d1
const r = await store.datalog(program, { useDefaultGraphAsUnion: true });

One caveat worth stating plainly: in the WebAssembly core the dialect is an off-by-default feature, because it costs about 0.2 MB and a Worker that does not use rules should not pay for it. The published @oxilite/d1 therefore ships without Datalog, and calling it raises a clear error telling you to rebuild the wasm with the datalog feature. The native @oxilite/node has it built in.

Limits to know

  • Aggregates must produce a value the term encoding can inline: COUNT, COUNT DISTINCT, SUM, MIN, MAX and SAMPLE work; AVG and GROUP_CONCAT are refused rather than silently approximated.
  • Non-linear components cost one request per round, need write access, and the relation may be at most six columns wide.
  • Out of scope: existential rules and unstratified negation.

The takeaway. If your question needs recursion with a join, a filter, a negation or a count in the middle of it, you no longer have to leave the query language and write a loop. Rules go in, one SQL statement comes out, and the answers are either returned or folded into the same inference set the OWL reasoner uses — on your laptop and on Cloudflare D1.
