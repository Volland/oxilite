JSON-LD · Verifiable Credentials · SPARQL · Cypher

Ask your credentials anything

JSON-LD documents and Verifiable Credentials are usually stored as blobs and searched by id. oxilite stores them as they are and also as a graph, so one SQLite file answers questions like “which accredited university issued this degree?”, “who works for the same employer?” or “what does any credential say about Bob?”, with SPARQL or with Cypher, on Node.js, Rust and Cloudflare D1.

A query tour · Every query below is checked by examples/jsonld-queries, on @oxilite/node and on D1

Three ways into the same document

When you store a JSON-LD document, oxilite writes it three times in one atomic write, and each copy answers a different kind of question:

Stored asAnswersQueried with
The exact JSON, under its key“Give me the credential as issued”, to present it or verify its proofget(key), documentForGraph(g)
A named graph of its RDF, named after the keyAnything about the claims: joins, aggregates, paths, reasoning, text searchSPARQL, Cypher
Indexed metadata: issuer, subject, types, validity windowThe everyday lookups: “valid credentials from this issuer”find(filter)

The graph is the interesting part. Because every document gets its own named graph, a query can always tell which document said what, and documents of different kinds (credentials, an issuer registry, your app's data) join like any other RDF.

The wallet

npm install @oxilite/node              # @oxilite/d1 for Workers; cargo add oxilite --features vc for Rust
import { Store } from "@oxilite/node";

const store = new Store({ path: "wallet.sqlite", textIndex: true });
const vcs = store.credentials();

vcs.put(degreeJson);                    // the W3C VCDM 2.0 degree example, with its Data Integrity proof
vcs.putPresentation(presentationJson);  // two achievement credentials, also stored on their own
vcs.put(bobMasterJson);                 // …and a master's degree and two employment credentials
vcs.put(aliceJobJson);
vcs.put(bobJobJson);

Next to the credentials, an issuer registry. It is not a credential, just a JSON-LD document with its own context. Contexts are loaded offline, so we register it once in the store:

const docs = store.jsonld();
docs.putContext("https://example.org/contexts/registry.jsonld", {
  "@context": { "@vocab": "https://example.org/registry#", accreditedBy: { "@type": "@id" } },
});
docs.put(JSON.stringify({
  "@context": "https://example.org/contexts/registry.jsonld",
  "@id": "https://example.org/registry",
  "@graph": [
    { "@id": "https://university.example/issuers/565049", name: "Example University",
      accreditedBy: "https://example.org/accreditors/eqar" },
    { "@id": "did:example:academy", name: "Example Academy" },
    { "@id": "did:example:acme", name: "ACME Corp" },
  ],
}));

A top-level @id with @graph names a graph in JSON-LD, so the registry lives in <https://example.org/registry>. The queries below use these prefixes:

PREFIX cred:   <https://www.w3.org/2018/credentials#>           # VC vocabulary: issuer, validFrom, credentialSubject…
PREFIX ex:     <https://www.w3.org/ns/credentials/examples#>  # terms of the VC examples context
PREFIX reg:    <https://example.org/registry#>
PREFIX schema: <https://schema.org/>
PREFIX xsd:    <http://www.w3.org/2001/XMLSchema#>

1Provenance: which credential says it?

GRAPH ?cred binds the graph a triple came from, which is the credential itself:

SELECT ?cred ?achievement WHERE {
  GRAPH ?cred { ?holder ex:achievement ?achievement }
  FILTER(isIRI(?cred))              # skip the presentation's embedded copies (blank-node graphs)
} ORDER BY ?achievement
cred            achievement
urn:uuid:vc-a   "Chess master"
urn:uuid:vc-b   "Go master"

No extra bookkeeping: provenance is simply the graph name.

2Join credentials with your own data

Credentials and the registry are different documents in different graphs, yet one query joins them: degrees issued by an accredited issuer, with the issuer's name from the registry.

SELECT ?holder ?degree ?issuerName WHERE {
  GRAPH ?cred { ?cred cred:issuer ?issuer ; cred:credentialSubject ?holder .
                ?holder ex:degree/schema:name ?degree }
  GRAPH <https://example.org/registry> { ?issuer reg:accreditedBy ?body ; reg:name ?issuerName }
} ORDER BY ?degree
holder                                  degree                                  issuerName
did:example:ebfeb1f712ebc6f1c276e12ec21 "Bachelor of Science and Arts"          "Example University"
did:example:bob                         "Master of Science in Graph Databases"  "Example University"

ex:degree/schema:name is a property path: it walks from the holder through the degree's blank node to its name. The academy's achievements are left out because the registry lists no accreditation for it.

3Aggregates

SELECT ?issuerName (COUNT(?cred) AS ?credentials) WHERE {
  GRAPH ?cred { ?cred a cred:VerifiableCredential ; cred:issuer ?issuer }
  FILTER(isIRI(?cred))
  GRAPH <https://example.org/registry> { ?issuer reg:name ?issuerName }
} GROUP BY ?issuerName ORDER BY DESC(?credentials) ?issuerName
issuerName            credentials
"ACME Corp"           2
"Example Academy"     2
"Example University"  2

Like every query in this tour, it compiles to a single SQL statement. On D1 that is one request, however many credentials the wallet holds.

4Validity windows, typed

The VC contexts type validFrom and validUntil as xsd:dateTime, and oxilite keeps a numeric timestamp for every date, so date comparisons are real comparisons, not string tricks. Employment credentials valid on 1 January 2026:

SELECT ?cred ?until WHERE {
  GRAPH ?cred { ?cred a ex:ExampleEmploymentCredential ; cred:validFrom ?from
                OPTIONAL { ?cred cred:validUntil ?until } }
  FILTER(?from <= "2026-01-01T00:00:00Z"^^xsd:dateTime
         && (!BOUND(?until) || ?until > "2026-01-01T00:00:00Z"^^xsd:dateTime))
}
cred              until
urn:uuid:bob-job  (open-ended)      # Alice's contract ended on 2024-12-31

For the common case there is a shortcut that needs no SPARQL (step 8).

5The holder's view

Turn the question around: what does any credential say about Bob? Blank nodes such as the degree are replaced by their name:

SELECT ?cred ?claim ?value WHERE {
  GRAPH ?cred { <did:example:bob> ?p ?o OPTIONAL { ?o schema:name ?name } }
  BIND(STRAFTER(STR(?p), "#") AS ?claim)
  BIND(COALESCE(?name, ?o) AS ?value)
} ORDER BY ?cred ?claim
cred              claim      value
urn:uuid:bob-job  employer   did:example:acme
urn:uuid:bob-job  jobTitle   "Data Engineer"
urn:uuid:bob-msc  degree     "Master of Science in Graph Databases"

6Reasoning over credential types

Issuers use specific types: ExampleBachelorDegree, ExampleMasterDegree. Your application thinks in degrees. Say so once, in the default graph:

ex:ExampleBachelorDegree rdfs:subClassOf ex:Degree .
ex:ExampleMasterDegree   rdfs:subClassOf ex:Degree .
const q = `SELECT ?name WHERE { GRAPH ?cred { ?d a ex:Degree ; schema:name ?name } }`;
store.query(q);                           // [] — no credential says "Degree"
store.query(q, { reasoning: "rdfs" });    // "Bachelor of Science and Arts", "Master of Science in Graph Databases"

Reasoning is a query rewrite against a small schema closure: nothing extra is written, the credentials' graphs stay exactly what the issuer signed, and the query is still one SQL statement. "owl-ql" adds inverse and equivalent properties.

7Full-text search inside claims

Open the store with textIndex: true and every string literal is in an SQLite FTS5 index, D1 included:

PREFIX oxl: <https://oxilite.dev/ns#>
SELECT ?cred ?title WHERE {
  GRAPH ?cred { ?holder ex:jobTitle ?title }
  FILTER(oxl:textMatch(?title, "engineer"))      # words, prefixes ("engin*"), phrases
}
cred                title
urn:uuid:bob-job    "Data Engineer"
urn:uuid:alice-job  "Knowledge Engineer"

8Lookups without SPARQL

The metadata columns answer the everyday questions with one indexed statement each, with keyset paging for large wallets:

vcs.find({ subject: "did:example:bob" });                              // bob-job, bob-msc
vcs.find({ issuer: "did:example:acme", validAt: new Date("2026-01-01") });  // bob-job
vcs.find({ type: "ExampleDegreeCredential" });                        // both degrees

const page1 = vcs.find({ profile: "vc2", limit: 2 });
const page2 = vcs.find({ profile: "vc2", limit: 2, after: page1.at(-1).key });

validAt reads validFrom/validUntil of VCDM 2.0 and issuanceDate/expirationDate of VCDM 1.1. On D1, where index entries are billed writes, you choose which metadata indexes exist.

9The same credentials as a property graph

oxilite also speaks openCypher, and Cypher sees the same triples. Set useDefaultGraphAsUnion and every credential graph becomes part of one property graph: types are labels, claims with literal values are properties, and claims pointing at other nodes are relationships.

const cypher = (q, params = {}) => store.cypher(q, params, {
  base: "https://www.w3.org/ns/credentials/examples#",   // names without a prefix
  prefixes: { cred: "https://www.w3.org/2018/credentials#", reg: "https://example.org/registry#",
              schema: "https://schema.org/" },
  useDefaultGraphAsUnion: true,
});

Who does which job, and for whom? Prefixed names go in backticks:

MATCH (c:ExampleEmploymentCredential)-[:`cred:credentialSubject`]->(p),
      (c)-[:`cred:issuer`]->(org)
RETURN p.jobTitle AS job, org.`reg:name` AS employer ORDER BY job
// [{ job: "Data Engineer", employer: "ACME Corp" }, { job: "Knowledge Engineer", employer: "ACME Corp" }]

Patterns are where Cypher shines. Colleagues are two holders whose employment credentials were issued by the same organisation, a five-node pattern that reads like the sentence:

MATCH (a)<-[:`cred:credentialSubject`]-(:ExampleEmploymentCredential)-[:`cred:issuer`]->(org),
      (org)<-[:`cred:issuer`]-(:ExampleEmploymentCredential)-[:`cred:credentialSubject`]->(b)
WHERE a.jobTitle < b.jobTitle
RETURN a.jobTitle AS a, b.jobTitle AS b, org.`reg:name` AS at
// [{ a: "Data Engineer", b: "Knowledge Engineer", at: "ACME Corp" }]

Aggregation and lists work as usual:

MATCH (c:`cred:VerifiableCredential`)-[:`cred:issuer`]->(i)
WHERE i.`reg:name` IS NOT NULL
RETURN i.`reg:name` AS issuer, count(DISTINCT c) AS credentials ORDER BY credentials DESC, issuer

MATCH (p)-[:degree]->(d)
RETURN p.jobTitle AS job, collect(d.`schema:name`) AS degrees ORDER BY job

The Cypher statements compile through the same SQL compiler, so they work on D1 as well. Cypher can write too, but credentials are signed documents: keep writes to your own data and let vcs.put own the credential graphs.

10See what a query costs

store.explain(`SELECT ?cred WHERE { GRAPH ?cred { ?s ex:achievement "Go master" } }`);
-- oxilite: fully compiled to SQL (1 output variable(s))
-- join order (heuristics, run optimize() for statistics): ?s ex:achievement "Go master" (~10 rows)
SELECT q1.g AS v0 FROM quads q1 WHERE q1.p = 986646405395019479 AND q1.o = 2229190399416023564 AND q1.g <> 0

Terms are hashed to integer ids in Rust, so the constants are plain integers and the query is an index scan on (p, o). explainCypher shows the same for Cypher.

And verification?

Querying finds credentials; deciding whether to trust one is a separate step, and it needs the credential exactly as signed. That is what the first copy is for. Whatever a query returns, you are one call away from the original bytes:

const [hit] = store.query(`SELECT ?cred WHERE { GRAPH ?cred { ?s ex:achievement "Go master" } FILTER(isIRI(?cred)) }`);
const { json, sha256 } = vcs.documents.documentForGraph(hit.get("cred"));   // byte for byte as stored

What oxilite checks itself:

  • Structure, on every put. The VCDM version from the first context, the context order, the VerifiableCredential type, issuer and subject (with the ssi-vc crate). A malformed credential is rejected and nothing is written.
  • Validity windows, with find({ validAt }) or the typed SPARQL filters above.
  • Graph integrity. documents.check() reports graphs that drifted from their JSON (after a SPARQL UPDATE, say), and rebuild() regenerates them.
  • Shapes. SHACL and ShEx validation of the stored graphs runs in Rust with oxilite-validate.

The cryptographic proof is checked by a Verifiable Credentials library on those stored bytes, for example Digital Bazaar's @digitalbazaar/vc with the eddsa-rdfc-2022 cryptosuite in JavaScript, or ssi in Rust:

import * as vc from "@digitalbazaar/vc";
import { DataIntegrityProof } from "@digitalbazaar/data-integrity";
import { cryptosuite } from "@digitalbazaar/eddsa-rdfc-2022-cryptosuite";

const result = await vc.verifyCredential({
  credential: JSON.parse(json),
  suite: new DataIntegrityProof({ cryptosuite }),
  documentLoader,                  // resolves contexts and the issuer's verification method
});
if (!result.verified) throw result.error;

Status-list revocation and enveloped (JOSE/COSE) credentials are not handled by oxilite either; they belong to the same verification step.

The takeaway. A credential store usually answers one question: “give me credential X”. With one named graph per document, oxilite answers all the others too (who said what, joined with your own JSON-LD, filtered by typed dates, widened by an ontology, searched as text, or matched as a Cypher pattern), and the signed JSON is still there, byte for byte, when it is time to verify.
