Property graphs on oxilite, with Cypher

Write CREATE (ada)-[:KNOWS {since: 2019}]->(grace), and query it back with Cypher or SPARQL. It's the same data in the same SQLite file, and it runs on Node.js, Rust and Cloudflare D1.

A walkthrough · The results in steps 1–5 are checked by examples/cypher-property-graph, on @oxilite/node and on D1

Two graph models, one store

Many developers think in property graphs: nodes with labels and properties, connected by typed relationships that have properties of their own. Cypher is the language most of them know. RDF describes the same world as triples, and adds what property graphs usually lack: global identifiers, named graphs for provenance, ontologies (OWL) and shapes (SHACL).

Normally you pick one model, or run two databases and keep them in sync. oxilite stores a property graph as RDF 1.2 and runs Cypher through the same compiler, planner and backends as SPARQL. That gives you:

  • data written with Cypher that SPARQL can read, and Turtle that Cypher can query;
  • Cypher everywhere oxilite runs: bundled SQLite, your own libsqlite3, and Cloudflare D1;
  • the store's ontology and shapes, applied to Cypher queries and writes.

The frontend passes 96.2% of the openCypher TCK (3,733 of 3,880 scenarios). The scenarios that fail are listed with their reason in tck-allowlist.txt. Most of them need user-defined procedures or reading after a write in one statement.

Setup

npm install @oxilite/node          # Node.js; @oxilite/d1 for Workers
cargo add oxilite --features cypher  # Rust
import { Store } from "@oxilite/node";

const store = new Store("graph.sqlite");   // or new Store() in memory
const options = { base: "http://example.com/" };
const cypher = (q, params = {}) => store.cypher(q, params, options);

base is the namespace for names: with it, the label :Person is the class <http://example.com/Person> and the key name is the property <http://example.com/name>. Without it, names go under urn:oxilite:pg:. You can also register prefixes (:`schema:Person`), map individual names, or write absolute IRIs in backticks.

1Build a graph

const r = cypher(`
  CREATE (ada:Person {name: 'Ada', born: 1815}),
         (grace:Person {name: 'Grace', born: 1906}),
         (alan:Person {name: 'Alan', born: 1912}),
         (acme:Company {name: 'Acme'}),
         (ada)-[:KNOWS {since: 2019}]->(grace),
         (grace)-[:KNOWS]->(alan),
         (ada)-[:WORKS_AT {role: 'engineer'}]->(acme),
         (grace)-[:WORKS_AT]->(acme)`);

r.stats  // { nodesCreated: 4, relationshipsCreated: 4, propertiesSet: 9, labelsAdded: 4, … }

The whole statement is one atomic write: one transaction natively, one batch() on D1. If any part fails, nothing is written.

2See what was stored

The property graph is ordinary RDF. Here is part of store.dump({ format: "application/n-quads" }), with the generated node IRIs shortened:

# a node: labels are rdf:type, properties are literal triples
<node:…-1> rdf:type rdfs:Resource .
<node:…-1> rdf:type ex:Person .
<node:…-1> ex:name "Ada" .
<node:…-1> ex:born 1815 .

# a relationship is a plain triple, used for traversal
<node:…-1> ex:KNOWS <node:…-2> .
# this one has a property, so it also has an RDF 1.2 reifier
<rel:…-5> rdf:reifies <<( <node:…-1> ex:KNOWS <node:…-2> )>> .
<rel:…-5> ex:since 2019 .

# no properties: just the triple, no reifier
<node:…-2> ex:KNOWS <node:…-3> .

Three choices shape this layout:

  • A relationship is always a plain triple. Following -[:KNOWS]-> is one join on a covering index, the same cost as a SPARQL triple pattern. Modelling each relationship as its own node would cost two joins per hop and three times the writes, which matters on D1, where every written index row is billed.
  • A reifier is added only when needed: when a relationship has properties, or when a second relationship of the same type connects the same two nodes. At that point both get reifiers, so parallel relationships stay distinct. Deleting the last one removes the triple too.
  • New nodes get fresh IRIs (urn:oxilite:node:…) and an rdfs:Resource marker. In RDF a resource exists only through its triples, so the marker keeps a node with no labels or properties from disappearing. labels() hides it.

SPARQL reads the result directly:

store.query(`PREFIX ex: <http://example.com/>
  SELECT ?name WHERE { ?p a ex:Person ; ex:name ?name } ORDER BY ?name`);
// → "Ada", "Alan", "Grace"

3Query it

Relationship properties

MATCH (p:Person)-[w:WORKS_AT]->(:Company {name: 'Acme'})
RETURN p.name AS name, w.role AS role ORDER BY name
// { name: "Ada",   role: "engineer" }
// { name: "Grace", role: null }

Grace's relationship has no reifier, so w.role is null, as in any Cypher database.

Relationship uniqueness

MATCH (a:Person)-[:WORKS_AT]->(c)<-[:WORKS_AT]-(b)
RETURN a.name, b.name ORDER BY a.name
// ["Ada", "Grace"], ["Grace", "Ada"]

Nobody is paired with themselves: within one MATCH, Cypher never uses the same relationship twice. oxilite compiles that rule into inequality filters on the relationship triples.

Variable-length and shortest paths

MATCH (:Person {name: 'Ada'})-[:KNOWS*1..3]->(f) RETURN f.name ORDER BY f.name
// "Alan", "Grace"

MATCH p = shortestPath((a:Person {name: 'Ada'})-[:KNOWS*]-(b:Person {name: 'Alan'}))
RETURN length(p) AS hops, [n IN nodes(p) | n.name] AS via
// { hops: 2, via: ["Ada", "Grace", "Alan"] }

A bounded pattern like *1..3 expands into one branch per length, with filters that stop a path from reusing a relationship. shortestPath is a breadth-first search that sends one SQL request per level for all start nodes at once. It doesn't need an interactive transaction, so it also runs on D1.

Aggregation, lists and values

MATCH (c:Company)<-[:WORKS_AT]-(p) WITH c, p ORDER BY p.name
WITH c, count(p) AS staff, collect(p.name) AS people
RETURN c.name AS company, staff, people
// { company: "Acme", staff: 2, people: ["Ada", "Grace"] }

MATCH (n:Person {name: 'Ada'})-[k:KNOWS]->() RETURN n, k
// n: { type: "node", labels: ["Person"], properties: { name: "Ada", born: 1815 }, id: "urn:oxilite:node:…" }
// k: { type: "relationship", relType: "KNOWS", properties: { since: 2019 }, start: …, end: … }

Temporal values follow openCypher too: date('2026-09-22') + duration('P1M') is 2026-10-22. They're stored as xsd:date, xsd:dateTime and xsd:duration, so SPARQL reads them as well. Lists and maps are stored as rdf:JSON literals.

4Change it

cypher(`
  MATCH (c:Company {name: 'Acme'})
  UNWIND $hires AS h
  MERGE (p:Person {name: h.name})
  CREATE (p)-[:WORKS_AT {role: h.role}]->(c)`,
  { hires: [{ name: "Alan", role: "researcher" }, { name: "Linus", role: "kernel" }] });
// Alan exists and is matched; Linus is created. { nodesCreated: 1, relationshipsCreated: 2 }

cypher("MATCH (p:Person {name: 'Grace'}) DELETE p");
// Error: cannot delete node …: it still has relationships (use DETACH DELETE)

cypher("MATCH (p:Person {name: 'Grace'}) DETACH DELETE p");
// { nodesDeleted: 1, relationshipsDeleted: 3 }: her reifiers go too

This is how a writing statement runs: it reads once, works out every change in Rust, then applies them all as one atomic request. Before writing, it checks which triples and reifiers the changes depend on. That's how it knows to give a new parallel relationship a reifier, and to refuse a DELETE that would leave relationships pointing at nothing.

5Start from RDF instead

The mapping works in both directions. Load existing RDF, with an ontology and SHACL shapes, and query it with Cypher:

store.load(`
  @prefix ex: <http://example.com/> . @prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
  @prefix sh: <http://www.w3.org/ns/shacl#> . @prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

  ex:Engineer rdfs:subClassOf ex:Person .
  ex:ada a ex:Engineer ; ex:name "Ada" ; ex:tag "math", "poetry" .
  ex:grace a ex:Person ; ex:name "Grace" .
  ex:ada ex:KNOWS ex:grace .

  ex:PersonShape a sh:NodeShape ; sh:targetClass ex:Person ;
    sh:property [ sh:path ex:name ; sh:minCount 1 ; sh:maxCount 1 ; sh:datatype xsd:string ] ;
    sh:property [ sh:path ex:born ; sh:datatype xsd:integer ] .`, { format: "text/turtle" });
MATCH (p {name: 'Ada'})-[:KNOWS]->(f) RETURN p, p.tag AS tags, f.name AS friend
// p.id: "http://example.com/ada"; tags: ["math", "poetry"]; friend: "Grace"

Nodes keep their own IRIs. A property with several RDF values, like ex:tag, reads as a list by default. You can set multiValue: "first" or "error" instead, and a property with sh:maxCount 1 always reads as a single value.

OWL: labels follow the class hierarchy

store.cypher("MATCH (p:Person) RETURN p.name ORDER BY p.name", {}, options);
// "Grace"
store.cypher("MATCH (p:Person) RETURN p.name ORDER BY p.name", {}, { ...options, reasoning: "rdfs" });
// "Ada", "Grace": Ada is an Engineer, and every Engineer is a Person

With reasoning: "rdfs", labels also match subclasses. With "owl-ql", relationship types also match subproperties and inverses, so -[:hasParent]-> finds pairs stored only as hasChild. The rewriting happens at compile time, with no extra requests.

SHACL: shapes as the schema

cypher("CREATE (:Person {name: 'Linus', born: 'ninety-nine'})");
// SHACL violation: node … (Person) property `born` must have datatype xsd:integer, got "ninety-nine"

cypher("CREATE (:Person {born: 1969})");
// SHACL violation: node … (Person) property `name` needs at least 1 value(s)

A writing statement checks every node it creates or changes against the shapes for its labels: sh:datatype, sh:minCount, sh:maxCount, sh:in and sh:pattern. The check runs before the write is sent, so an invalid statement changes nothing. Shapes also help reads. Load them once with Store::cypher_schema() and pass them in the options: a required property then joins without OPTIONAL, and a typed property needs one typed comparison instead of one per possible type. CALL db.labels(), db.relationshipTypes(), db.propertyKeys() and db.schema.nodeTypeProperties() answer from the shapes and the data. Complete SHACL and ShEx validation remains available through rudof.

How a Cypher query runs

oxilite doesn't have a separate Cypher engine. A statement goes through these steps:

  1. It's parsed and checked (scopes across WITH, and Cypher's static rules).
  2. It's planned into two parts: everything SQL can express, and a tail that runs in Rust for things SQL can't do (writes, list and map expressions, collect(), temporal arithmetic).
  3. The SQL part is lowered to SPARQL algebra and compiled by oxilite's existing SPARQL-to-SQL compiler, with the same statistics planner, reasoning rewrites and fallback.
  4. A job runs the SQL, fetches the labels and properties of the nodes and relationships in the result in one more batched request, runs the tail, and applies any writes.

store.explainCypher() shows all of it. Here's the roles query from step 3, after store.optimize() collected statistics (IRIs shortened):

-- SPARQL (compiled to SQL):
SELECT ?c1_p ?c3_ws ?c4_wp ?c5_wo ?c6_wr WHERE { ?c1_p rdf:type ex:Person . ?c2_anon rdf:type ex:Company .
  ?c2_anon ex:name "Acme" . ?c1_p ex:WORKS_AT ?c2_anon .
  OPTIONAL { ?c6_wr rdf:reifies <<( ?c1_p ex:WORKS_AT ?c2_anon )>> } … }
-- evaluated in Rust: RETURN
-- oxilite: fully compiled to SQL (5 output variable(s))
-- join order (statistics): ?c2_anon rdf:type ex:Company (~1 rows) → ?c2_anon ex:name "Acme" (~0 rows)
--   → ?c1_p ex:WORKS_AT ?c2_anon (~2 rows) → ?c1_p rdf:type ex:Person …
SELECT q3.s AS v0, … FROM quads q1 CROSS JOIN quads q2 CROSS JOIN quads q3 CROSS JOIN quads q4
  LEFT JOIN (quads q5 JOIN triple_terms tt6) ON (…) WHERE …

The planner starts from the one company, not from every person, and the whole MATCH is a single SQL statement. For shortestPath, the explain output also says "breadth-first search, one SQL request per level", and it warns when a pattern would produce a Cartesian product.

Reusing the SPARQL compiler is the reason Cypher arrived with a planner, reasoning, four backends and D1 support already in place. The alternative, a native layout with nodes and edges tables, would make relationship properties cheaper. It would also need a second planner and a second set of backends, lose SPARQL over the same data, and have no standard mapping for OWL and SHACL.

The same code on Rust and D1

// Rust: features = ["cypher"]
use oxilite::cypher::{CypherOptions, Params, Vocabulary};

let store = oxilite::store::Store::open("graph.sqlite")?;
let options = CypherOptions { vocabulary: Vocabulary::new("http://example.com/"), ..Default::default() };
let r = store.cypher_with("MATCH (a:Person)-[:KNOWS]->(b) RETURN b.name", &Params::new(), &options)?;
// Cloudflare Worker with @oxilite/d1
const store = await D1Store.open(env.DB, { wasm, migrated: true });
const r = await store.cypher("MATCH (a:Person)-[:KNOWS]->(b) RETURN b.name", {}, { base: "http://example.com/" });

The example runs steps 1–5 on @oxilite/node and on a local D1 through Miniflare, and asserts the same results on both (node test.mjs).

Limits to know

  • Reading after a write in one statement. A MATCH after CREATE, MERGE or another clause that runs in Rust is rejected as unsupported. Put the MATCH first, as in step 4, or split the work into two statements.
  • Isolation on D1. A writing statement reads, then sends one atomic batch. On D1, another writer can change the data between the read and the batch. Natively, both happen in one transaction.
  • Not included: the Bolt protocol and Neo4j drivers, user-defined procedures such as APOC, owl:sameAs in matching, and full GQL.

The takeaway. Your property graph is RDF, stored in SQLite. Write it with Cypher or Turtle, query it with Cypher or SPARQL, and let the ontology and shapes you already have shape the answers and guard the writes. The same code runs on your laptop and on Cloudflare D1.
