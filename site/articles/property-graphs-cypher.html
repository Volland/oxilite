Property graphs on oxilite: the Cypher frontend

Nodes with labels, relationships with properties, and MATCH (a)-[:KNOWS]->(b), stored in the same SQLite quads that SPARQL queries. Here's how the mapping works, what you can build with it today, and what the Cypher frontend adds.

Design and status · Specification: openspec/changes/m7-cypher

Status. The Cypher frontend is milestone M7 and is in development: the parser, the vocabulary and the lowering to oxilite's compiler are being built now. The Cypher examples below follow the specification and may change before release. Everything under "Build it today" runs on the current release.

Two graph models, one store

Many developers think in property graphs: nodes with labels and properties, connected by typed relationships that carry properties of their own. Cypher is the query language most of them know. RDF describes the same world with triples, and adds things property graphs lack: global identifiers, named graphs for provenance, ontologies (OWL) and shapes (SHACL).

You usually have to pick one model, or copy data between two databases and keep them in sync. oxilite takes a different route. It stores a property graph as RDF 1.2 and compiles Cypher into the same SQL compiler, planner and backends that SPARQL already uses. The result is one dataset with two query languages:

  • data written with Cypher can be read with SPARQL, and RDF loaded as Turtle can be read with Cypher;
  • Cypher runs everywhere oxilite runs: bundled SQLite, your own libsqlite3, and Cloudflare D1;
  • the ontology and shapes in the store also apply to Cypher queries.

The mapping

RDF 1.2 added triple terms and reifiers: a node that stands for a statement and can carry properties of its own. That's exactly what a property-graph relationship needs, so the mapping is direct:

Property graphRDF 1.2 in oxilite
NodeAn IRI or a blank node
Label :Personrdf:type triple: ex:ada a ex:Person
Node propertyLiteral triple: ex:ada ex:name "Ada"
Relationship -[:KNOWS]->Asserted triple: ex:ada ex:KNOWS ex:grace
Relationship propertyOn a reifier: _:r rdf:reifies <<( ex:ada ex:KNOWS ex:grace )>> ; ex:since 2019
Parallel relationshipsSeveral reifiers of the same triple term
List or map propertyAn rdf:JSON literal, handled by SQLite's JSON functions
Names (labels, types, keys)IRIs from a configurable vocabulary: a base IRI, prefixes and overrides

Two design choices keep this fast on SQLite, and cheap on D1, where every written index row is billed:

  • A relationship is always a plain triple. Following -[:KNOWS]-> is one join on a covering index, the same cost as a SPARQL triple pattern. The alternative, a node per relationship, costs two joins per hop and triples the writes.
  • A reifier is created only when needed: when the relationship has properties, when a second, parallel relationship of the same type connects the same nodes, or when a query needs the relationship's identity. Most relationships in real graphs have no properties, and they never pay for one.

Build it today with RDF 1.2 and SPARQL

The storage side of the mapping already works in the current release, because oxilite supports RDF 1.2 triple terms. Here is a small company graph as a property graph, written in Turtle 1.2. The ~ reifier {| … |} annotation syntax asserts a triple and describes it in one step.

company.ttl 
PREFIX ex: <http://ex/>

ex:ada   a ex:Person  ; ex:name "Ada" .
ex:grace a ex:Person  ; ex:name "Grace" .
ex:acme  a ex:Company ; ex:name "Acme" .

ex:ada ex:KNOWS    ex:grace ~ ex:k1 {| ex:since 2019 |} .
ex:ada ex:WORKS_AT ex:acme  ~ ex:w1 {| ex:role "engineer" ; ex:from 2021 |} .
ex:grace ex:WORKS_AT ex:acme .                # a plain relationship: no reifier
oxilite load -l company.sqlite -f company.ttl

Who works at Acme, and in what role? The relationship property sits on the reifier, so it's read with an OPTIONAL. Grace's relationship has no properties, and she still appears:

PREFIX ex: <http://ex/>
PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
SELECT ?name ?role WHERE {
  ?p a ex:Person ; ex:name ?name ; ex:WORKS_AT ?c .
  ?c ex:name "Acme" .
  OPTIONAL { ?r rdf:reifies <<( ?p ex:WORKS_AT ?c )>> ; ex:role ?role }
} ORDER BY ?name
# name    role
# "Ada"   "engineer"
# "Grace"

oxilite explain shows the query is one SQL statement. The planner starts from the rarest pattern, the company named "Acme", and walks out from there. The reifier lookup joins through the triple_terms table:

-- oxilite: fully compiled to SQL (2 output variable(s))
-- join order (statistics): ?c ex:name "Acme" (~1 rows) → ?p ex:WORKS_AT ?c (~2 rows)
--   → ?p rdf:type ex:Person (~1 rows) → ?p ex:name ?name (~1 rows)
-- join order (statistics): ?r ex:role ?role (~1 rows) → ?r rdf:reifies <<( ?p ex:WORKS_AT ?c )>> (~1 rows)
SELECT q4.o AS v1, q5.o AS v5
FROM quads q1 CROSS JOIN quads q2 CROSS JOIN quads q3 CROSS JOIN quads q4
LEFT JOIN (quads q5 CROSS JOIN quads q6 JOIN triple_terms tt7) ON (…)
WHERE q1.p = … AND q1.o = … AND q2.o = q1.s AND …

This is a real property graph, and you can use it now from Rust, Node.js, the CLI or a D1 Worker. What's missing is the Cypher syntax on top.

The same graph in Cypher

With the Cypher frontend, the graph above is one CREATE. Names map to IRIs through the store's vocabulary; with the base IRI http://ex/, :Person becomes ex:Person and name becomes ex:name.

planned API 
store.cypher(`
  CREATE (ada:Person {name: 'Ada'}),
         (grace:Person {name: 'Grace'}),
         (acme:Company {name: 'Acme'}),
         (ada)-[:KNOWS {since: 2019}]->(grace),
         (ada)-[:WORKS_AT {role: 'engineer', from: 2021}]->(acme),
         (grace)-[:WORKS_AT]->(acme)
`);

That statement writes the same quads the Turtle file did: two relationships with reifiers, one without. The whole statement is one atomic request, which is a single batch() on D1. New nodes get fresh ids computed inside SQL, with no read-back, so UNWIND range(1, 100) AS i CREATE (:Item {i: i}) also creates 100 nodes in one batch.

The role query becomes:

MATCH (p:Person)-[w:WORKS_AT]->(:Company {name: 'Acme'})
RETURN p.name, w.role
ORDER BY p.name
// "Ada"    "engineer"
// "Grace"  null

It compiles to the same kind of single SQL statement as the SPARQL version, with the same planner choosing the join order. The specification requires this: a MATCH without variable-length or shortest paths must compile to one statement whenever the equivalent SPARQL would.

Cypher semantics, preserved

Cypher isn't just SPARQL with arrows. A few of its rules need their own handling, and the design covers each:

  • Relationship uniqueness. Within one MATCH, a relationship can't be used twice. So MATCH (a:Person)-[:WORKS_AT]->(c)<-[:WORKS_AT]-(b) RETURN a.name, b.name finds colleagues without pairing Ada with herself. The compiler adds pairwise inequality of relationship identities: the reifier, or the (s, p, o) triple when there's no reifier.
  • Variable-length paths. MATCH (:Person {name: 'Ada'})-[:KNOWS*1..3]->(f) RETURN f.name reuses the recursive SQL that SPARQL property paths already use. It adds a depth column and a record of visited relationships, so a path never repeats a relationship. Unbounded patterns have a depth cap, and explain() warns about them.
  • Shortest paths. shortestPath is a breadth-first search that sends one request per frontier level. It doesn't need an interactive transaction, so it works on D1.
  • Result values. RETURN p gives a node with its labels and properties, and RETURN w a relationship with its type, endpoints and properties. They're built in one extra batched request for all rows.
  • Several values for one property. RDF allows ex:tag "a", "b", and Cypher expects one value per key. A per-store policy reads these values as a list (the default), keeps the first, or raises an error.

Writes

MERGE (p:Person {name: 'Linus'})
  ON CREATE SET p.source = 'import'

MATCH (a:Person {name: 'Ada'}), (l:Person {name: 'Linus'})
CREATE (a)-[:KNOWS {since: 2024}]->(l)

MATCH (n:Person {name: 'Linus'}) DETACH DELETE n

CREATE, MERGE, SET, REMOVE, DELETE and DETACH DELETE each run as one atomic request. They use the same staging table as SPARQL's DELETE/INSERT … WHERE, so the reading part is evaluated before anything changes. DETACH DELETE also removes the reifiers of the node's relationships. Deleting one of two parallel relationships removes only its reifier and keeps the shared triple. A DELETE of a node that still has relationships fails, and leaves the store unchanged.

What RDF gives Cypher

Because the property graph is RDF, it can use the ontology and the shapes stored beside it. That's hard to get from a native property-graph engine.

OWL: smarter matching

With the same per-query reasoning option SPARQL uses, labels and relationship types are rewritten through the ontology at compile time. That needs no extra requests and no extra writes.

# in the store
ex:Employee rdfs:subClassOf ex:Person .
ex:hasParent owl:inverseOf ex:hasChild .

// with reasoning: "rdfs"
MATCH (p:Person) RETURN p              // also returns every ex:Employee

// with reasoning: "owl-ql"
MATCH (c)-[:hasParent]->(p) RETURN c, p  // also finds pairs stored only as p ex:hasChild c

SHACL: shapes as the schema

Property graphs are usually schemaless. RDF has SHACL, and oxilite uses registered shapes as the property-graph schema:

  • sh:maxCount 1 makes a property a scalar, so it's never read as a list;
  • sh:minCount 1 lets the compiler use an inner join instead of a LEFT JOIN;
  • sh:datatype gives a property a static type, which simplifies generated comparisons;
  • simple constraints (datatype, cardinality, class, sh:in, simple patterns) are checked inside the same batch as a write. A CREATE (:Person {age: 'old'}) against a shape that requires an integer age fails as a whole, on D1 too;
  • CALL db.labels(), db.relationshipTypes() and db.schema() are answered from the shapes and the planner statistics.

Complete SHACL and ShEx validation stays with rudof, as it does for SPARQL users today.

Why not a separate graph engine?

The obvious alternative is a native property-graph layout: nodes and edges tables with JSON properties. It would make relationship properties cheaper. It would also mean a second storage engine across four backends, a second planner, no SPARQL over the same data, and an invented OWL and SHACL layer. The project estimates that at 30–40 person-weeks, against 22–29 for the frontend, and it would win only for write-heavy workloads dominated by relationship properties that need none of RDF's features. Building Cypher as a second frontend keeps one store, one planner and one set of backends, and every improvement to them helps both languages.

Out of scope for the first release: full GQL (the syntax tree is designed to grow into it), the Bolt protocol and Neo4j drivers, owl:sameAs, point and duration types, and APOC-style procedures.

Start now. Model your property graph in RDF 1.2 as shown above: labels as types, relationships as triples, and relationship properties on reifiers. It works with SPARQL today, and it's the layout the Cypher frontend is specified to read and write. Use the same base IRI for your names, and Cypher can read the data directly when it lands.
