What history costs on D1

On Cloudflare D1 every row written is billed, index entries included. So the question behind oxilite's versioning was never whether a store could keep its history. It was how many rows that history costs. The answer: nothing for a store clock, two rows per change for a full, immutable, queryable log, and nothing at all for stores that don't want history.

The constraints

  • Rows are money. D1 bills rows written, and each index entry is a row. A plain oxilite store writes 4.81 rows per triple: the quad, its three permutation indexes, and the term dictionary amortised.
  • A batch is the only transaction. db.batch() is D1's one atomic unit. oxilite already compiles every write, DELETE/INSERT … WHERE included, into one self-reading batch.
  • One writer. A D1 database has a single primary that applies writes in order. That turned out to be the most useful property of all.
  • No extensions, and limits. Only plain SQL, at most 50 statements per batch, and statements under about 100 KB.

Almost every query asks about now, so now must not get slower. With the log beside quads, a store only reads history when a query names a past version.

The log writes itself

oxilite has many writers: SPARQL updates, bulk loads, quad inserts, Cypher writes, JSON-LD documents and credentials, and the studio. Teaching each of them to log would be a bug waiting for the next writer. The log is written by triggers on quads instead, so it records what actually happened to the table, whoever did it.

Triggers also give no-op detection for free. INSERT OR IGNORE of a quad that is already present fires no AFTER INSERT trigger, and a DELETE that matches nothing fires no AFTER DELETE. Re-asserting what you already know costs zero log rows. A quad added and removed within the same batch deletes its own log row instead of adding a second, so each batch records its net effect.

The log is immutable because the database enforces it. BEFORE UPDATE and BEFORE DELETE triggers abort on any row older than the batch being written. The only exception is an explicit purge for erasure requests, which is itself recorded.

A clock with no coordination

Each atomic write gets a tick, and that tick is the commit. The store, not the writer, prepends two statements to every batch that writes quads. The first writes the tick's time, author and message as terms, so the history can be queried as RDF. The second opens the tick:

INSERT INTO ticks(t, time, kind, author, message)
  SELECT coalesce(max(t), 0) + 1, /* now */ …, 0, 'ada', 'close t1' FROM ticks

Because D1 has one writer, max(t) + 1 never goes backwards. There are no client clocks to skew, no counter row to contend on, and no round trip to fetch a number. The tick carries its wall time for @2026-09-01T… queries, but ordering never depends on clocks. Triggers and inserts read the current tick with (SELECT max(t) FROM ticks), which is one index probe.

The price is two statements: a versioned store's batches keep two of D1's 50 statements for the tick, so bulk loads chunk to 48. Stores without versioning keep all 50.

Why write terms at all? A term's id is a hash computed in Rust, so SQL can't mint an id for a new literal. The tick's time, author and message are known in Rust when the tick opens, so they are written then. A commit itself is identified by its tick as an integer, the one kind of id SQL can compute. That is what lets the history graph and Datalog's history relations be plain SQL over the log, with no stored copy.

A timestamp that costs nothing

The stamped level records on every quad the tick that added it. That sounds like an update per quad, but it isn't one. The stamp is a column, quads.t, filled by the insert itself (… SELECT column1, …, (SELECT max(t) FROM ticks) FROM (VALUES …)). D1 bills rows, not bytes, so a wider row costs nothing extra.

Adding the column to an existing store is an ALTER TABLE … ADD COLUMN, which SQLite does in its metadata without rewriting a row. The column is not part of any secondary index, so every triple-pattern scan stays index-only. Measured: 4.82 rows per triple against 4.81 unversioned. The difference is three rows per batch (the tick, its time term and that term's index entry), and nothing per triple.

Why genesis holds the whole store

Raising a store to log copies every quad into the log as the genesis commit. The shortcut is tempting. A quad with no log entries must have been there since the log started, so why copy it?

Because the shortcut stops being true. Lower the level for a while (the log freezes), write, then raise it again. A quad added during the gap has no log entries either, and the shortcut would place it in versions from before it existed. We caught this case while designing the resume, and it decided the question. With a recorded genesis, the log alone describes every version. A freeze is a boundary. A resume records the gap's net changes as one commit against the frozen state, and a query that asks for a version inside the gap gets an error that names it. The genesis costs one log row per quad, once. For a store created versioned, it is free.

The tx index is what makes history browsable: it answers "what did commit 42 change" and "every change since 40" without scanning the log. The optional as-of index adds predicate-first and object-first orders, so as-of queries with an unbound subject use an index instead of scanning. Buy it if you query the past often. Otherwise the plain log answers the same questions with more reads.

Choosing a level

If you read the past often, add the as-of index (asOfIndex: true, --as-of-index). It costs 8.82 rows per triple instead of 6.82.

  • off if nothing needs to know what changed. Most caches and derived stores fall here.
  • stamped if you need "what's new since" and who wrote it, but not "what did it look like". It fits incremental exports, search indexing and sync feeds, at no extra rows per triple.
  • log if you need to answer questions about the past: audit, agent memory, curated graphs, undoing an import. It costs 42 % more rows written. Reads of the present cost the same.

Levels change by migration

Opening a store never changes its level. Starting history is a snapshot, billed once, and deleting history cannot be undone, so neither may happen because a flag in a config file changed. On D1, where schema changes go through migrations, the change is a migration file:

npx oxilite-d1 schema --versioning log > migrations/0001_oxilite.sql            # a new database
npx oxilite-d1 versioning-migration --from off --to log > migrations/0002_versioning.sql   # an existing one
npx wrangler d1 migrations apply my-graph --remote

The Worker then opens the store with { migrated: true } and picks up the level the database records. Lowering a level freezes the history and keeps it readable. Deleting it takes an explicit --allow-loss.

A D1 detail worth knowing

The first version of the capture triggers passed every test on the bundled SQLite and then failed on D1 with near "AS": syntax error. SQLite forbids an alias on the target table of a DELETE inside a trigger body. The bundled SQLite accepted it anyway, and D1 enforces the rule. The versioning suite now runs the same scenario on the bundled SQLite, the system SQLite, the D1 code path and a real local D1, so a difference like that fails a test instead of a deploy.

What reading the past costs

A version is the set of quads whose latest logged change at or before its tick is an addition: a log scan with one NOT EXISTS probe on the log's key. It compiles into the same single SQL statement as any other query. bench as-of-latency times the same queries on the present and on a version 250 commits back. The store has 80,000 triples, 500 commits and 95,724 log rows, on the bundled SQLite, and each figure is the median of 15 runs in ms:

QueryPresentPast, plain logPast, as-of index

Three findings:

  • The present costs the same at every level. An unversioned store's queries also compile to exactly the SQL they compiled to before versioning existed, which a golden test pins for the W3C query and update corpus.
  • The plain log is fast only when the subject is bound. Its key starts with the subject, so a pattern bound only by predicate or object scans the whole log. The as-of index fixes that, bringing selective patterns to 1–3.6×, for two more rows written per change.
  • Aggregating a predicate's whole history stays slower, 17×, because every historical row pays a probe. Checkpoints, meaning materialized snapshots every n commits, would bound it. They are the first design question for branches, which read every non-checked-out branch through the log. A BEAR-B run will confirm these synthetic numbers before branches are built.

The takeaway. History on D1 is priced in rows. oxilite keeps the present untouched, records the past with triggers, and numbers commits with a clock that needs no coordination because D1 has one writer. A timestamp costs zero rows per triple, a complete log costs two, and a store that doesn't opt in costs nothing.
