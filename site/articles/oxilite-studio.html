oxilite studio: a workbench for knowledge graphs

Knowledge graphs are usually edited in one tool, queried in a second, validated in a third and reasoned over by a fourth, and none of them knows where a triple came from. oxilite studio puts the whole loop in the editor you already use: write Turtle, and the store, the reasoner and the validator follow you as you type.

A guide · Version 0.1 · The behaviour on this page is asserted by the studio server's tests (crates/oxilite-cli/src/studio) · Extension source: Volland/oxilite-studio

1Install

oxilite studio is a VS Code extension. Search for oxilite studio in the Extensions view, or:

code --install-extension pavlyshyn.oxilite-studio

The engine is not JavaScript: it is oxilite studio-server, a Rust language server built from the same crates as oxilite itself, and the extension bundles it for your platform. Version 0.1 ships builds for macOS (Apple silicon and Intel). On Linux and Windows, build the server yourself and tell the extension where it is:

git clone https://github.com/Volland/oxilite && cd oxilite
cargo build --release -p oxilite-cli
# VS Code setting:  "oxilite.server.path": "/path/to/oxilite/target/release/oxilite"

The same binary gives you oxilite check for CI and oxilite mcp for agents, both covered below.

2Open a folder

Open any folder with RDF in it. The studio loads every .ttl, .nt, .nq, .trig, .n3, .rdf and .owl file into a Project store, a scratch SQLite database in .oxilite/studio.sqlite that it keeps out of git for you. Each file gets its own named graph, and queries see their union.

Nothing needs configuring at first. A file with SHACL shapes in it is treated as shapes, not data. A file declaring an owl:Ontology is treated as an ontology, and a .dl file as Datalog rules. Save a file and only its graph is reloaded; a syntax error loads nothing from that file and appears in the Problems panel at the parser's position.

The oxilite sidebar shows what was loaded. Connections lists the Project store and any stores you attach. The Store Explorer has the graphs, the class hierarchy with instance counts, properties by use, files with their roles, and prefixes. Query History keeps what you ran.

3Query with your own vocabulary

Open a .rq file and start typing. Completion knows where you are in a triple: in predicate position it offers the store's predicates in the order the data uses them, after a only classes, and a prefix you have not declared yet completes with the PREFIX line added to the top of the query, using the prefix your Turtle files already use.

PREFIX ex: <http://ex.org/>
SELECT * { ?x ex:▌   → ex:name  (10 uses)   ex:knows  (3 uses)

Hover an IRI to see its label, comment, types and where it is defined; Go to Definition jumps to the Turtle line where it is described, even from a query file. A predicate the store never uses gets a warning, because it is almost always a typo.

Cmd/Ctrl+Enter runs the file or the selection; results appear beside the editor in a table that renders only the rows on screen, and CONSTRUCT results can switch to a graph view. Cmd/Ctrl+Shift+E shows the SQL the query compiles to and the planner's join order. The same keys run a Datalog program's goal in a .dl file and a Cypher statement in a .cypher file. Cypher names resolve against your data's own namespace, so MATCH (a:Person)-[:knows]->(b) means ex:Person and ex:knows.

4Reasoning that explains itself

Pick a reasoning profile from the status bar: rdfs and owlql rewrite queries, and owl2rl materializes the closure. Your rule files are materialized too. Each producer, OWL 2 RL or a rule file, keeps its own conclusions, so editing one rule file does not wipe the others: oxilite now attributes every inferred triple to the producer that derived it.

Take an ontology, some data and one rule:

# onto.ttl
@prefix ex: <http://ex.org/> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
ex:Manager  rdfs:subClassOf ex:Employee .
ex:Employee rdfs:subClassOf ex:Person .

# data.ttl
@prefix ex: <http://ex.org/> .
ex:ann a ex:Manager .
ex:ann ex:manages ex:bo .

# rules/boss.dl
ex:boss(?y, ?x) :- ex:manages(?x, ?y), ex:Person(?x).

Open ex:bo in the resource view (right-click an IRI, Open Resource View) and the statement ex:bo ex:boss ex:ann carries a badge: inferred: rules/boss.dl. Click why?:

inferred  ex:bo ex:boss ex:ann
  by rules/boss.dl: <…boss>(?y, ?x) :- <…manages>(?x, ?y), <…Person>(?x).
  ├─ asserted  ex:ann ex:manages ex:bo          data.ttl:3
  └─ inferred  ex:ann rdf:type ex:Person
       by owl2rl: cax-sco (subclass)
       └─ …  down to  ex:ann a ex:Manager  (data.ttl:2)  and the subclass axioms in onto.ttl

A rule's conclusion is explained by running that rule's body again in the Datalog engine with its head bound to the triple. An OWL or RDFS conclusion is explained by rule templates run as SPARQL. Either way the tree ends at statements you wrote, and each one opens at its line.

5SHACL on the line that broke it

Shapes validate in the background after every change, and each result is a diagnostic on the data line, linked to the shape that failed. With a reasoning profile on, validation sees inferred triples, which is what SHACL means but most tools skip:

# shapes.ttl
ex:PersonShape a sh:NodeShape ;
  sh:targetClass ex:Person ;
  sh:property [ sh:path ex:name ; sh:minCount 1 ] .

# staff.ttl
ex:carol a ex:Employee ; ex:name "Carol" .
ex:dan a ex:Employee .                     ⚠ sh:minCount violated on ex:name

Without reasoning nobody is an ex:Person, so the data conforms. Switch to rdfs and employees become persons, so ex:dan gets a squiggle on line 3 of staff.ttl. The shapes file itself is never loaded as data, so your queries do not see it. ShEx works the same way: pair a .shex schema with a shape map of the same name. The SHACL report view groups results by shape or by focus node.

6A manifest, tests, and CI

When conventions are not enough, an oxilite.toml at the root takes over completely. It names graphs, roles, the reasoning profile, and tests:

reasoning = "owl2rl"

[[graph]]
iri   = "https://ex.org/g/people"
files = ["data/*.ttl"]

[shapes]
files = ["shapes/*.ttl"]

[rules]
files = ["rules/*.dl"]

[[test]]
name   = "people have names"
query  = "tests/names.rq"
expect = "tests/names.srj"          # SPARQL results; "Update Snapshot" writes it

[[test]]
name = "bad person rejected"
data = "tests/bad.ttl"                 # a fixture, validated with the project's ontologies
expect_violations = ["ex:PersonShape"]

[[test]]
name        = "ancestry is transitive"
entails     = "tests/yes.ttl"
not_entails = "tests/no.ttl"

The tests appear in VS Code's Test Explorer at their line in the manifest. A failing query test shows expected and actual results as a diff, and Update Snapshot rewrites the expected file. The same checks run without an editor:

$ oxilite check
oxilite check: 3 files, 6 triples, reasoning owl2rl
pass    people have names: results match
pass    bad person rejected: http://ex.org/PersonShape (1 results)
pass    ancestry is transitive: entailments hold
ok

When a result changes, the failing test says what is missing and what is unexpected, row by row, and the run ends with FAILED.

It exits with status 1 on any load error, rule error, SHACL violation or failing test, and --json prints the report for CI annotations. It runs exactly the code the editor runs, so CI and your editor agree.

7Real stores: SQLite and Cloudflare D1

The Project store is derived from your files and is thrown away on reload. To work on a real database, attach it from the Connections view:

  • A SQLite file. Any oxilite store, read-only or read-write.
  • A local D1 database. The file wrangler dev keeps under .wrangler/state.
  • A remote D1 database. Over Cloudflare's HTTP API, with the token in VS Code's secret storage. It opens read-only unless you ask otherwise.

Every query, completion and explain works on an attached store. Writes are guarded: an update, a writing Cypher statement or an import asks first, and on D1 the question says what it will cost (about 10 billed rows written (2 quads) for a two-triple INSERT DATA), since D1 bills every written index entry. Each result on D1 reports the requests it took and the rows it read and wrote. OWL 2 RL materialization on D1 is a separate, confirmed command, because it runs over several requests and is not atomic across them.

8Notebooks, diagrams and a rules debugger

  • Notebooks (.oxnb) mix Markdown with SPARQL, Datalog and Cypher cells. Their outputs are saved in the file and drawn with the same table and graph views.
  • The ontology diagram draws classes with their datatype properties and instance counts, subclass links, and object properties from domain to range.
  • Debug Rules on a .dl file lists each rule with how many ways its body matches and how many facts its head holds. A rule that matches nothing, or explodes, stands out next to its line.
  • Full-text search runs oxl:textMatch over string literals. Set text_index = true in the manifest and it uses the FTS5 index.

9Give your agent the graph

oxilite mcp serves the studio's operations as Model Context Protocol tools: sparql_query, datalog_query, schema, validate, why and reload. It loads the project the way the studio does. The extension registers it for your workspace, and Copy MCP Server Config gives the same entry for other agents:

{ "mcpServers": { "oxilite": { "command": "oxilite", "args": ["mcp", "--root", "/path/to/project"] } } }

Answers are compact text an agent reads well: tab-separated tables, N-Triples, validation results with file and line, and proof trees. An agent that calls schema first writes queries in your vocabulary instead of guessing it.

How it is built

The extension is a thin TypeScript client. Everything else runs in oxilite studio-server, one Rust process speaking the Language Server Protocol, for three reasons:

  • Isolation. A long materialization or a crash cannot take the editor down, and reads and validation run on worker threads.
  • One engine. SHACL and ShEx come from rudof, OWL 2 RL, Datalog and Cypher from oxilite, all linked directly.
  • One code path. oxilite check and oxilite mcp reuse the same code, so the editor, CI and agents agree.

A lenient scanner tokenizes half-typed text and guesses each term's role in its triple, which drives completion. A source-position index remembers where every IRI occurs, which drives go-to-definition and puts SHACL results on the right line. Views render plain JSON payloads, which is why a notebook can save its outputs.

Limits to know

  • macOS builds only in 0.1. Linux and Windows need the server built from source for now, as above.
  • Results are capped, not paged. The table shows the first 10 000 rows (the oxilite.query.rowLimit setting).
  • Justifications use rule templates for OWL 2 RL. Class expressions and property chains are reported as inferred without their premises.
  • Materialization runs in the foreground. Validation and queries are backgrounded and cancelled by newer changes, but re-materializing a large OWL 2 RL closure blocks the server while it runs.
  • D1 is tested against a stand-in. The D1 backend's tests use a local double of the /raw endpoint, not Cloudflare itself.

The takeaway. A knowledge graph deserves the loop code gets: completion that knows your names, errors on the line that caused them, tests in CI. oxilite studio gives RDF that loop, and adds what only a knowledge graph needs: every inference can tell you why it is there.
