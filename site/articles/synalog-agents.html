Synalog · Datalog · Agents · Time travel

A semantic layer for agents, over your knowledge graph

oxilite has had its own Datalog since 0.3. Version 0.9 adds a second rule language beside it: Synalog, the Datalog-family language built for AI agents. You write unmodified Synalog programs, and they run over your RDF triples as if the triples were tables — on your laptop, in Python, in Node.js and on Cloudflare D1, and against any past version of the graph.

A walkthrough · Every program and result on this page comes from the test suite (store.rs, synalog.test.ts) or from the oxilite command line

Why a second rule language

Synalog is a Rust rewrite of Google's Logica, built by Synalinks around one idea: give an agent a semantic layer it can write to. Instead of re-deriving "who is an active customer" in every query, the agent defines it once as a named concept, builds more concepts on top of it, and has every rule it writes checked by a verifier whose error messages are meant to be read by a model. The language has named arguments, full expressions, aggregation in the rule head, functors, and @OrderBy / @Limit, so results can be read a page at a time. It compiles to SQL for seven engines and ships an agent skill.

That is a different job from oxilite's own Datalog, which is about rules over the graph: its atoms are triple patterns, it derives sets of RDF terms, and what it concludes can be written back as triples. We did not want to pick one, so oxilite now runs both over the same quads.

How Synalog differs from oxilite's Datalog

oxilite DatalogSynalog on oxilite
AtomsPositional and RDF-native: ex:parent(?x, ?y) is the triple patternNamed arguments over tables: parent(subject: x, object: y)
ValuesRDF terms, compared by term idSQL values: numbers, strings, 1/0 for booleans
SemanticsSetsMultisets; a rule marked distinct gets set semantics
RecursionTrue least fixpoint: WITH RECURSIVE, or iterated in a work table when SQLite can't express itUnrolled to the depth set by @Recursive(P, N), all in one statement (up to N = 20 on the store)
ExpressionsSPARQL's expression language in constraintsArithmetic, strings, if … then … else, lists, records, built-in functions
AggregationIn the head, stratified; results must be storable as termsIn the head: +=, Min=, Max=, Avg=, List=, Set=, …
ResultThe goal's solutions, as termsThe rows of a named predicate, ordered and pageable
MaterializationYes, into the inference table SPARQL and Cypher readNo: results are values, not triples
Time travel@version for a whole program, and at "REF" per atomasOf for the whole program

In short: reach for Datalog when the conclusions should become part of the graph, and for Synalog when an agent is building and querying a vocabulary of concepts over the graph. The two compose, as step 5 shows.

1The triple store, seen as tables

Synalog reads tables by their lower-case names. On oxilite, every program can read one called triples:

triples(subject, predicate, object, kind, datatype, lang, graph)
Parent(child:, parent:) :-
  triples(subject: child, predicate: "http://example.org/parent", object: parent);

This returns the three parent pairs as IRIs. There is no triples table in the schema, though. When a program uses it, oxilite adds it to the front of the compiled statement as a common table expression over the quad table. It honours the same options as SPARQL: the default graph only unless you ask for the union of all graphs, and inferred triples only if you ask for them.

The key decision was how terms become values. oxilite stores every term as a 64-bit id. Synalog, however, compares and computes with ordinary SQL semantics, and SQLite sorts every string after every number, so comparing lexical forms would make age > 18 quietly wrong. So the object column is decoded into a real SQL value:

$ oxilite synalog D -l kg.db -p 'D(s:, o:, kind:, datatype:, lang:) :-
    triples(subject: s, object: o, kind:, datatype:, lang:), s == "http://example.org/bob";'
s                       o                       kind     datatype                                               lang
http://example.org/bob  http://example.org/cy   iri
http://example.org/bob  Bob                     literal  http://www.w3.org/1999/02/22-rdf-syntax-ns#langString  en
http://example.org/bob  17                      literal  http://www.w3.org/2001/XMLSchema#integer

Integers come out as numbers, and inline integers are decoded from the id itself without a lookup. Other numeric literals become numbers, booleans become 1 and 0, blank nodes read as _:label, and IRIs and strings read as text. The RDF details are kept in kind, datatype and lang, so an agent can still tell the IRI http://… from a string with the same text. The graph column is NULL for the default graph. Now numbers behave like numbers:

Age(p:, age:) :- triples(subject: p, predicate: "http://example.org/age", object: age);
Adult(p:) :- Age(p:, age:), age > 18;               # ada, cy
Total(t? += age) distinct :- Age(age:);             # 138

2Declared tables, answered by the index

Filtering triples by a predicate string works, but it decodes every quad before comparing. So a program can declare a table for one predicate or one class:

# @table parent <http://example.org/parent>
# @class person <http://example.org/Person>

Parent(child:, parent:) :- parent(subject: child, object: parent);
Childless(p:) distinct :- person(subject: p), ~parent(subject: p);

A declared table compiles to WHERE q.p = 680058446304702762. That number is the predicate's term id, computed in Rust, so the posg index answers the lookup directly. The declarations are Synalog comments, which means the program is still valid Synalog and still runs unchanged with Synalog's own CLI against any other database. You can also pass the same declarations from code: { tables: [{ name: "parent", predicate: "…" }] }.

3Recursion, and what it compiles to

# @table parent <http://example.org/parent>
@Recursive(Ancestor, 10);
Ancestor(x:, y:) distinct :- parent(subject: x, object: y);
Ancestor(x:, y:) distinct :- Ancestor(x:, y: m), parent(subject: m, object: y);

On the four-person chain this returns six pairs, exactly what the SPARQL property path ex:parent+ returns. The test suite uses that property path as the reference answer. Synalog handles recursion differently from oxilite's Datalog. It doesn't run a fixpoint; it unrolls the recursion into one common table expression per level, up to the bound. That's why the bound is mandatory and why cyclic data still terminates. distinct matters here: without it Synalog keeps duplicate rows, and a cycle multiplies them at every level.

This is the start of the statement oxilite synalog Ancestor --sql prints (the long decoding CASE expressions are shortened):

WITH parent AS NOT MATERIALIZED (
       SELECT /* decode q.s */ AS subject, /* decode q.o */ AS object, … AS graph
       FROM quads AS q WHERE q.p = 680058446304702762 AND +q.g = 0),
     t_8_Ancestor_…_f1 AS (SELECT … FROM parent AS t_10_parent),
     t_7_Ancestor_r0   AS (SELECT … GROUP BY x, y),
     t_5_Ancestor_…_f2 AS (SELECT … FROM t_7_Ancestor_r0, parent WHERE parent.subject = Ancestor_r0.y
                           UNION ALL SELECT … FROM parent),
     …
SELECT x, y FROM … ORDER BY x, y

Everything below the first CTE is Synalog's own output; oxilite doesn't touch Synalog's compiler. It prepends the store tables the statement uses, marked NOT MATERIALIZED so SQLite can push filters into them, and it makes the SQL portable. Synalog's SQLite dialect assumes the Logica Python runtime has registered helper functions on the connection. Its negation, for instance, compiles to MIN(MagicalEntangle(1, …)) IS NULL. D1 cannot register functions at all, so oxilite rewrites the helpers that plain SQLite can express (MagicalEntangle, IN_LIST, JOIN_STRINGS, DistinctListAgg, SortList). The ones it can't — ArgMax=, file and model calls, and @Ground, which creates tables — are rejected before anything runs, with an error naming the construct. So is a @Recursive bound above 20, because above 20 Synalog switches to an iterative mode that writes tables. The result is one statement and one round trip, on every backend.

4Time travel

On a store with versioning turned on, a Synalog program can run against any past version. Here the chain was written in two commits, and dee arrived in the second:

$ oxilite synalog Ancestor -l kg.db -f anc.l
x                       y
http://example.org/ada  http://example.org/bob
http://example.org/ada  http://example.org/cy
http://example.org/ada  http://example.org/dee
http://example.org/bob  http://example.org/cy
http://example.org/bob  http://example.org/dee
http://example.org/cy   http://example.org/dee

$ oxilite synalog Ancestor -l kg.db -f anc.l --as-of HEAD~1
x                       y
http://example.org/ada  http://example.org/bob
http://example.org/ada  http://example.org/cy
http://example.org/bob  http://example.org/cy

This works because every store table is built over a single quad source, and asOf only swaps what that source is. Instead of quads, the tables read the relation oxilite's versioning already computes from the change log: each quad whose latest change at or before that tick was an addition. The version reference is resolved to a tick first — HEAD~1, #42 or @2026-09-01T00:00:00Z — and then the program compiles against it. Synalog doesn't know any of this is happening. The same program, unchanged, reads the past.

store.synalog(program, "Ancestor", { asOf: "HEAD~1" });          // Node.js, D1
store.synalog(program, "Ancestor", as_of="HEAD~1")            # Python
store.synalog_with(program, "Ancestor", &Options { as_of: Some("HEAD~1".into()), ..Default::default() })?; // Rust

Two limits, stated plainly. The version applies to the whole program: Synalog has no per-atom at "REF" like oxilite's Datalog, so comparing two versions in one program is still a Datalog job. And inferences describe only the present, so asOf combined with includeInferred is refused.

5Named graphs, and rules from the other language

With useDefaultGraphAsUnion, the tables read every graph, and the graph column carries each row's graph IRI (NULL for the default graph). With includeInferred, they also read the inference table, which is where the two rule languages meet. Datalog can write conclusions as triples, and Synalog can then build on them:

// Datalog: store grandparents as triples
store.datalogMaterialize(`@prefix ex: <http://example.org/> .
  ex:grandparent(?x, ?z) :- ex:parent(?x, ?y), ex:parent(?y, ?z).`);

// Synalog: read them like any other predicate
store.synalog(`# @table grandparent <http://example.org/grandparent>
  G(x:, y:) :- grandparent(subject: x, object: y);`, "G", { includeInferred: true });
// ada → cy, bob → dee

Everywhere oxilite runs

// Rust — oxilite = { version = "0.9", features = ["synalog"] }
let r = store.synalog(program, "Ancestor")?;       // columns + rows of SQL values
let sql = store.synalog_sql(program, "Ancestor")?;
// Node.js
const r = store.synalog(program, "Old");
r.records   // [{ p: "http://example.org/ada", age: 42 }]
# Python
r = store.synalog(program, "P", tables={"par": EX + "parent"}, limit=1, offset=1)
# Command line
oxilite synalog Ancestor -l kg.db -f anc.l                 # run
oxilite synalog Ancestor -l kg.db -f anc.l --sql           # the SQL it runs on the store
oxilite synalog Ancestor -f anc.l --engine duckdb          # Synalog's own SQL for another engine

That last line is the dialect on its own: compile_for_engine and check need no store and cover all seven of Synalog's engines. @oxilite/d1 has the same synalog() method, but as with Datalog, the WebAssembly core only includes it when built with the synalog feature. It adds about 2 MB, and a Worker that doesn't use it shouldn't pay for it. D1's own limits are checked before anything is sent: a statement over the length limit, or a predicate with more than five rules (D1 allows five terms in a compound SELECT), fails with a Synalog error rather than an opaque SQLite one.

Limits to know

  • Not on the store: ArgMax= / ArgMin=, @Ground, file, solver and model calls, and @Recursive bounds above 20. Each is rejected up front, by name.
  • Values, not terms: results can't be materialized as triples. Use oxilite's Datalog for conclusions that should become part of the graph.
  • Decoding costs a lookup for every term that isn't stored inline. Declared tables avoid scanning, not decoding.
  • Triple terms (RDF 1.2) read as NULL for now.

The takeaway. An agent can now write the semantic layer it knows how to write — named concepts, composable rules, pages of ordered results — directly over a knowledge graph, without an export or an ETL step, and ask the same questions of the graph as it was yesterday. oxilite's Datalog is still there for rules whose conclusions belong in the graph. Both compile to one SQL statement over the same quads.
