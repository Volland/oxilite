Time travel for your knowledge graph

A knowledge graph that forgets is hard to trust. What did the agent believe on Monday? Who closed this ticket? Which import broke the ontology? oxilite can now keep a store's whole history inside the same SQLite file or D1 database, and answer SPARQL and Datalog queries about any past version.

A walkthrough · The behaviour on this page is asserted by the test suite: versioning.rs (bundled SQLite, system SQLite, the D1 code path and Miniflare D1), versioning.test.ts and versions.rs

1Off by default, three levels when you want it

Most stores do not need history, and on Cloudflare D1 every row written is billed. So versioning is a per-store choice, and a store without it is exactly the store you had before: the same tables, the same SQL and the same bill. When you do want history, pick a level:

LevelWhat the store keepsRows written per triple on D1
off (default)The current state only4.81
stampedA store clock. Every write is a tick with a time, an author and a message, and every quad records the tick that added it.4.82, no extra row per triple (three per batch)
logAn immutable change log: every addition and removal, so any past version can be queried6.82

The levels nest. log keeps everything stamped keeps, and you can raise or lower a live store's level later. The costs are measured, not estimated. The design article explains where each row comes from, and the benchmarks show what reading the past costs. Every option is listed in the reference.

2Create a versioned store

# the CLI: any write creates the file; --versioning applies to a new store
oxilite update -l kb.sqlite --versioning log --author ada -m "seed tickets" \
  -u 'PREFIX ex: <http://example.com/> INSERT DATA { ex:t1 ex:status "open" . ex:t2 ex:status "open" }'

oxilite update -l kb.sqlite --author bob -m "close t1" \
  -u 'PREFIX ex: <http://example.com/> DELETE { ex:t1 ex:status ?s } INSERT { ex:t1 ex:status "done" } WHERE { ex:t1 ex:status ?s }'

The same from Rust, where one call is one commit:

use oxilite::version::{CommitInfo, Versioning};

let store = Store::open_with_options("kb.sqlite", StoreOptions {
    versioning: Versioning::Log,
    ..Default::default()
})?;
store.with_commit(
    CommitInfo { author: Some("ada".into()), message: Some("seed tickets".into()) },
    |s| s.update(SEED),
)?;
store.update(CLOSE_T1)?;

From JavaScript, on Node.js or on D1:

const store = await D1Store.open(env.DB, { wasm, versioning: "log" });
await store.withCommit({ author: "ada", message: "seed tickets" }, (s) => s.update(SEED));

Every atomic write is one commit: a SPARQL update, a load batch, a Cypher write, a JSON-LD document. The history is recorded by triggers underneath the store, so no write path can skip it. Writes that change nothing are not recorded, such as re-adding a quad that is already there. A quad that one update removes and then re-adds leaves no trace either.

3Read the history

$ oxilite versioning log -l kb.sqlite
#4  2026-09-25T06:59:35.839Z  +1 -1  close t1  (bob)
#3  2026-09-25T06:59:35.829Z  +2 -0  seed tickets  (ada)
#2  2026-09-25T06:59:35.827Z  [genesis]  history starts
#1  2026-09-25T06:59:35.826Z  [level]  versioning: stamped

Each entry is a tick: a number that only grows, its wall time, what it added and removed, the message and the author. Level changes are ticks too. Genesis is where the recorded history starts, and it holds the whole store at that moment, so every later version can be rebuilt from the log alone.

4Query the past

Any query can run against any version. A version is HEAD, HEAD~n (n commits back), a tick such as #3, or an instant such as @2026-09-25T06:59:35.830Z:

$ oxilite query -l kb.sqlite --results-format tsv -q 'SELECT ?t ?s { ?t <http://example.com/status> ?s }'
?t                        ?s
<http://example.com/t2>   "open"
<http://example.com/t1>   "done"

$ oxilite query -l kb.sqlite --as-of HEAD~1 --results-format tsv -q 'SELECT ?t ?s { ?t <http://example.com/status> ?s }'
?t                        ?s
<http://example.com/t1>   "open"
<http://example.com/t2>   "open"

Past versions are read from the log. With a subject bound, they take about 3× as long as the present. Other patterns need the optional as-of index: with it, they stay within 1–3.6× (see the numbers). In code, the option is as_of (QueryOptions::as_of in Rust, { as_of: "HEAD~1" } in JavaScript), and oxilite serve accepts /query?version=HEAD~1. The whole query sees that version: patterns, property paths, OPTIONAL, GRAPH and DESCRIBE. It still compiles to one SQL statement. Asking for a version the store never recorded is an error: a version before the history began, or one inside a gap left by a freeze (see step 7). You never get a silently wrong answer.

5Compare two versions in one query

SPARQL already has syntax for reading another dataset inside a query: SERVICE. oxilite treats <oxilite:version/REF> as another version of the same store, so a single query can join the present with the past:

SELECT ?t ?old ?new WHERE {
  ?t <http://example.com/status> ?new
  SERVICE <oxilite:version/HEAD~1> { ?t <http://example.com/status> ?old }
  FILTER(?old != ?new)
}
?t                        ?old    ?new
<http://example.com/t1>   "open"  "done"

This is ordinary SPARQL 1.1, so any parser accepts it, and it still compiles to one SQL statement. For the raw difference there is diff, printed as RDF Patch lines:

$ oxilite versioning diff -l kb.sqlite HEAD~1
# #4
A <http://example.com/t1> <http://example.com/status> "done" .
D <http://example.com/t1> <http://example.com/status> "open" .

changes --since 40 prints every change after tick 40 in order: a change feed for incremental exports, search indexes or caches. A stamped store has no log but can still answer "what was added since tick 40", with no extra cost per write.

6Rules over the past

Datalog programs read a version with one directive:

@version "HEAD~1" .
@prefix ex: <http://example.org/> .
anc(?x, ?y) :- ex:parent(?x, ?y).
anc(?x, ?z) :- ex:parent(?x, ?y), anc(?y, ?z).
?- anc(ex:ada, ?y).

Or pass it as an option (asOf in JavaScript, --as-of on the CLI). Recursion, negation and aggregation work as usual. Materialized inferences describe only the present, so combining them with a version is refused, and so is materializing from the past.

A single atom can read another version too. at "HEAD~1" compares values across versions. at ?c reads the version of a commit that another atom binds, which gives the value a fact had at every commit:

changed(?t, ?old, ?new) :- ex:status(?t, ?new), ex:status(?t, ?old) at "HEAD~1", ?old != ?new.
status_at(?c, ?v)       :- commit(?c, _, _, _), ex:status(ex:t1, ?v) at ?c.

Cypher takes the same option, so a property-graph query can read the past as well: store.cypher("MATCH (t:Ticket) RETURN t.status", {}, { asOf: "HEAD~1" }). A writing statement with a version is refused.

7Ask the history itself

The history is data too. In SPARQL it is a graph, <oxilite:history>. Each commit is described with PROV-O: its time, its author, its message and the commit before it. Each change is a triple term:

PREFIX prov: <http://www.w3.org/ns/prov#>
PREFIX oxl:  <https://oxilite.dev/ns#>
SELECT ?who ?when WHERE { GRAPH <oxilite:history> {
  ?c oxl:removed <<( ex:alice ex:role ex:admin )>> ;
     prov:wasAssociatedWith ?who ;
     prov:startedAtTime ?when } }

That asks who revoked Alice's admin role, and when. Replace the constants with variables, <<( ?s ?p ?o )>>, and you get every change with its author. A commit is identified by its tick, an integer, the same number as #42. Datalog reads the same history as relations: commit(?c, ?parent, ?time, ?author), added(?s, ?p, ?o, ?g, ?c), removed(…) and branch(?name, ?c):

removed_by(?t, ?v, ?who) :- removed(?t, ex:status, ?v, _, ?c), commit(?c, _, _, ?who).

8Change the level later

oxilite versioning set -l kb.sqlite log        # raise: the store becomes the genesis commit
oxilite versioning set -l kb.sqlite stamped    # lower: history freezes, still queryable up to the freeze
oxilite versioning set -l kb.sqlite log        # raise again: the gap is recorded as one commit
oxilite versioning set -l kb.sqlite off --allow-loss   # delete the history, the ticks and the stamp column

Opening a store never changes its level. A configuration file that says --versioning log will not quietly start billing a production database for a snapshot. Only an explicit level change, or a migration on D1, raises or lowers it. Upgrades never lose a quad. Downgrades keep the history frozen and read-only unless you pass --allow-loss. When you raise the level again, the net changes made during the gap are recorded as one commit. The history stays exact, and queries inside the gap fail and name it.

9When history must forget

An immutable log conflicts with an erasure request. oxilite has one operation that rewrites history, and it is deliberately explicit:

oxilite versioning purge -l kb.sqlite --subject http://example.com/alice \
  --reason "erasure request #1142" --yes

The matching quads disappear from the store, from every past version and from the change feed. The purge itself is recorded with its reason and author, but without the removed content. The log is otherwise immutable. Updating or deleting its rows fails with history is immutable, and that is enforced by the database, not by the library.

Where it helps

  • Agent memory. Ask what the agent believed before a bad ingestion, diff it, and check the commit messages to see which tool wrote what.
  • Curated knowledge graphs. Reviewers see exactly which triples a change added and removed, with its author and reason.
  • Audit. Answer "what did we know at the time of this decision" with a query, not by restoring a backup.
  • Incremental sync. Feed search indexes and caches from changes instead of re-scanning the store.

Not yet

  • Branches and merge, and pushing or pulling history between stores, are planned as version-branches and version-sync. The design and its measured costs are in the archived first phase.

The takeaway. Turn versioning on per store, and every write becomes a commit you can query, diff and attribute, in the same SQLite file or D1 database. With it off, nothing changes.
