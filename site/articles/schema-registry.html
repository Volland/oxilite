Ontologies · SHACL · Reasoning

Tell the store which graphs are schema

In most triple stores an ontology is just more triples: you cannot list what is loaded, version it, switch it off, or reason under one ontology instead of all of them. oxilite 0.3.0 lets a graph declare what it is — and the store acts on it.

A design note · The behaviour on this page is asserted by schema_registry.rs and validate.rs · Rust API

Update. The registry described here has since become RDF: registrations are triples in the system graph <oxilite:schema> in the published oxl: vocabulary, each schema can be mapped to the graphs it describes, and the shell, CLI, Node and D1 all reach it. Read Graphs that describe graphs. The schema_graphs table below is migrated automatically when a store is opened.

Two problems that are the same problem

Load an ontology into a triple store and something odd happens: it vanishes into the data. It is triples in the same table as everything else, so the store has no idea it is schema. Concretely, before 0.3.0 you could not ask oxilite which ontologies were loaded, pin a version, drop one cleanly, or reason under a chosen ontology rather than the union of every axiom in the database. Reasoning found its axioms by sniffing predicates — anything anywhere that looked like rdfs:subClassOf counted.

SHACL shapes had a sharper version of the same problem: two sources of truth. The Cypher frontend read shapes from the dataset by running a SPARQL query — once per writing statement, which on D1 is a network round trip per write. The validator took shapes as a string from outside the store. So the same shapes could be stored and ignored by the validator, or used by the validator and absent from the store entirely.

Both are the same missing concept: a graph whose role is schema rather than data.

1Register a graph

use oxilite::schema::{Registration, SchemaRole};

store.register_schema_graph(
    NamedNodeRef::new("http://example.com/onto")?,
    SchemaRole::Ontology,
    &Registration::new()
        .with_iri(NamedNode::new("http://example.com/onto")?)
        .with_version("2026-09"),
)?;

store.schema_graphs()?;   // [RegisteredGraph { graph, role, registration, loaded_at }]

The roles are Ontology, Shacl and Shex. Registering records a role, an optional ontology IRI, a version, a content digest and an import list — and moves nothing. The graph's triples stay exactly where they were, ordinary RDF that SPARQL reads and updates:

SELECT ?o WHERE { GRAPH <http://example.com/onto> { ex:Dog rdfs:subClassOf ?o } }
-- still answers ex:Animal

That is deliberate. SHACL shapes are RDF and people query them; moving schema into a private table would break that, and GRAPH ?g already gives you the separation for free. Registering also makes lifecycle cheap — drop_schema_graph removes the registration and every quad of the graph in one atomic request, with no read first.

2Reason under the ontologies you choose

Now the registration does work. Two ontology graphs, one of which you do not currently trust:

// ex:good says  Dog ⊑ Animal      ex:bad says  Rock ⊑ Animal
store.register_schema_graph(good, SchemaRole::Ontology, &Registration::new())?;
store.register_schema_graph(bad,  SchemaRole::Ontology, &Registration::new())?;

// ?x a ex:Animal  with RDFS reasoning → ex:rex, ex:granite

store.set_schema_graph_active(bad, false)?;

// same query → ex:rex only

Deactivating withdraws exactly that ontology's entailments; reactivating restores them, with no reloading of data. An axiom written to a graph that is not registered as an ontology now entails nothing at all — which is the point: you decide what counts as schema, instead of the store guessing from predicates.

The mechanism is a single SQL subquery inside the existing closure statements, so this costs no extra round trip and the closure is still rebuilt inside the same atomic request as the write that changed it.

3An empty registry means every graph

The compatibility rule that makes this safe to ship: every scoping predicate reads "the active graphs of this role, or every graph while none is registered." A store that registers nothing behaves exactly as it did before the registry existed — same entailments, same results. Registering your first ontology is the act that narrows the scope.

So this is purely additive. Nothing you have breaks by upgrading, and you opt in when you want the control.

4Keep axioms out of data queries

Anyone who has loaded a real ontology knows this annoyance: SELECT ?s ?p ?o over your data now returns fifty thousand axioms.

let opts = QueryOptions { include_schema_graphs: false, ..Default::default() };
// registered schema graphs drop out of every pattern scan

It defaults to true — the dataset is the dataset — and switching it off covers the default graph, GRAPH ?g, property paths and OPTIONAL alike, because every quad source in the compiler goes through one place. Hiding ignores the active flag, since an inactive ontology graph is still schema and still noise. named_graphs() and the dumps are untouched.

5Shapes, compiled once

The second half of the release fixes the two-sources-of-truth problem. The SHACL property shapes of the registered shapes graphs are compiled into an index — target class, path, sh:datatype, sh:minCount, sh:maxCount, sh:pattern, the sh:in values, and whether the shape is relationship-valued:

store.shape_index()?;   // one request, no SPARQL evaluation

It is a cache with the same discipline the reasoning closure already follows: rebuilt by pure INSERT … SELECT statements over the quads — an rdf:rest*/rdf:first recursive CTE walks sh:in — by optimize() and, inside the same atomic request, by any write that touches a SHACL predicate. Write a shape and the index already knows about it; no rebuild step, no staleness window.

Two consumers now read that one index:

  • Cypher reads its property-graph schema from it in one indexed request, instead of evaluating a SPARQL query per writing statement. On D1 that is the difference between one round trip and a compiled query on every write.
  • The validator can be driven by shapes held in the store, rather than a string you pass in:
use oxilite_validate::{validate_shacl_stored, ShaclValidationMode};

let report = validate_shacl_stored(&store, None, &ShaclValidationMode::Native)?;

With None the registry decides, and it refuses to guess: exactly one registered SHACL graph is used, none is an error, more than one is an error naming the candidates. Pass a graph explicitly to override. The shapes are handed to rudof's own parser, so a stored shapes graph and a shapes file compile identically — a property the test suite asserts by comparing the two reports.

Why register rather than separate

The obvious alternative was separate ontology_quads and shape_quads tables. It was rejected for three reasons, and they are worth stating because they explain the whole shape of the feature:

  • SHACL shapes are RDF that people query — a private table breaks that, and named graphs already separate them;
  • a second table would force a UNION into every pattern scan, which is precisely what the compiler exists to avoid;
  • no new index on quads means no extra write cost on D1, where every written index entry is billed.

The registry is one small table that labels a graph. Everything else falls out of that.

Limits to know

  • Rust only, for now. The registry is not yet exposed in @oxilite/node or @oxilite/d1, and there is no CLI subcommand for it. The behaviour it drives — scoped reasoning, the shape index behind Cypher — applies everywhere; the registration calls are Rust.
  • owl:imports is recorded, not resolved. The registry stores the import list; it does not fetch them.
  • One closure, not one per ontology. The registry decides which graphs feed the closure, not how many closures exist.
  • A stale sh:in corner. rdf:first/rdf:rest are deliberately not refresh triggers — they would rebuild the shape index on every write touching any RDF list anywhere. Appending to an existing sh:in list without touching a sh: predicate leaves the index stale until the next optimize().
  • On D1, adding tables needs a migration. A D1 store is opened with open_existing, so no DDL runs per request. 0.3.0 adds four tables; regenerate and apply a migration before upgrading an existing database, as the @oxilite/d1 README describes.

The takeaway. Your ontology and your shapes stop being anonymous triples. Declare a graph's role once and reasoning narrows to the ontologies you trust, axioms stay out of your data queries, and Cypher and the SHACL validator read one compiled source of truth instead of two different ones. A store that registers nothing behaves exactly as before.
